📖 The Anatomy of a Class

A class in UML is depicted as a rectangle divided into three compartments:

  1. Top: Class name (bold and centered)
  2. Middle: Attributes (fields/variables)
  3. Bottom: Operations (methods/functions)
mermaid
classDiagram
    class User {
        -String username
        -String password
        -int age
        +login(password) boolean
        +updateProfile() void
    }

👁️ Visibility Markers

Visibility markers define access levels, enforcing encapsulation:

MarkerVisibilityMeaning
+PublicAccessible from any other class
-PrivateAccessible only within the class itself
#ProtectedAccessible within the class and its subclasses
~PackageAccessible within the same package

📝 Syntax Rules

1. Attributes

Syntax: visibility name: Type [multiplicity] = DefaultValue

[!example] Examples

  • + age: int = 21 (public integer with default 21)
  • - name: String (private string)
  • # activeTokens: List [0..*] (protected list of tokens)

2. Methods

Syntax: visibility name(param1: Type1, ...): ReturnType

[!example] Examples

  • + calculateTotal(amount: double): double
  • - isAdult(age: int): boolean
  • + printReceipt(): void

🧩 Special Class Types

1. Interfaces

An interface defines a contract. It uses the <<interface>> stereotype.

mermaid
classDiagram
    class Payable {
        <<interface>>
        +calculatePay() double
    }

2. Abstract Classes

An abstract class cannot be instantiated. It is denoted by the <<abstract>> stereotype, and its name is written in italics (though standard tools often just use the stereotype for clarity).

mermaid
classDiagram
    class Animal {
        <<abstract>>
        +makeSound()* void
        +sleep() void
    }

(Note: Abstract methods are also often italicized or marked with an asterisk).

3. Enumerations (Enums)

An enum is a fixed set of named values. It uses the <<enumeration>> stereotype.

mermaid
classDiagram
    class OrderStatus {
        <<enumeration>>
        PENDING
        CONFIRMED
        SHIPPED
        DELIVERED
    }

🔍 Perspectives of Class Diagrams

Depending on who you are showing the diagram to, you might include different levels of detail:

  1. Conceptual Perspective: For Business Analysts. Shows just the class names and relationships (no attributes/methods).
  2. Specification Perspective: For System Architects. Shows interfaces, abstract classes, and key public methods (the "contract").
  3. Implementation Perspective: For Developers. Complete, code-level view with all private variables, visibility markers, and exact data types.

[!quote] Key Takeaway UML class notation is a universal language. Mastering the syntax (+, -, #, data types, and stereotypes) allows you to translate code into diagrams, and diagrams into code effortlessly.
