📌 Dependency Injection Concepts

[!info] Navigation Module: [[10 - Dependency Injection/index|← Dependency Injection Overview]]

🛑 The Problem: Hardcoded Logic

Imagine building an OrderService. If it creates its own dependencies, they are hardcoded:

cpp
class OrderService {
    InventoryService inventory;
    RazorpayPayment payment;

public:
    OrderService() 
        : inventory(InventoryService()), payment(RazorpayPayment()) {}

    void checkout() {
        // ... logic
    }
};

Issues with this approach:

  1. Rigidity: To switch from Razorpay to Stripe, we must modify the OrderService code.
  2. Untestable: We cannot easily test OrderService without hitting the actual RazorpayPayment API.
  3. Tight Coupling: High-level OrderService depends heavily on low-level implementations.

🔑 What is Dependency Injection?

Dependency Injection (DI) is a pattern where an object receives its dependencies from an external source rather than creating them itself.

[!example] Restaurant Analogy 👨‍🍳 A chef needs vegetables to cook. Instead of growing the vegetables in the kitchen (creating dependencies), a supplier delivers them (injecting dependencies). The chef focuses purely on cooking.

Advantages of DI

  • Swappable Components: Easily swap implementations (e.g., Stripe for Razorpay).
  • Testability: Inject mock objects for unit testing.
  • Follows SOLID: Directly supports the Dependency Inversion Principle (D) and Open/Closed Principle (O).

🛠️ Types of Dependency Injection

1. Constructor Injection (Recommended)

Dependencies are passed via the constructor. This is the most common and robust form.

Pros:

  • Dependencies are immutable.
  • Ensures the object is fully initialized and ready to use.
  • Thread-safe.
cpp
class OrderService {
    std::shared_ptr<PaymentService> payment;

public:
    explicit OrderService(std::shared_ptr<PaymentService> payment)
        : payment(std::move(payment)) {}
};

2. Setter Injection

Dependencies are passed via setter methods after object creation.

Pros:

  • Allows for optional or mutable dependencies (can be changed at runtime). Cons:
  • The object might be used before the dependency is set, leading to null pointer exceptions.
cpp
class OrderService {
    std::shared_ptr<PaymentService> payment;
public:
    void setPayment(std::shared_ptr<PaymentService> p) { payment = std::move(p); }
};

3. Interface Injection (Rare)

The dependency provides an injector method that forces the client to implement an interface. It is rarely used due to unnecessary complexity and code bloat.

⭐ Best Practices in C++

  1. Depend on Abstractions: Inject pointers to pure virtual base classes (Interfaces), not concrete classes.
  2. Use Smart Pointers: Use std::shared_ptr or std::unique_ptr to manage the lifecycle of injected dependencies cleanly.
  3. Composition Root: Only create concrete objects at the very top level of your application (like main()), and inject them down. The rest of your application should only know about interfaces.

Example of the Composition Root Pattern

cpp
// 1. Contract
class NotificationService {
public:
    virtual void send(const string& msg) = 0;
    virtual ~NotificationService() = default;
};

// 2. Concrete Implementation
class EmailService : public NotificationService {
    void send(const string& msg) override { cout << "Email: " << msg << "\n"; }
};

// 3. Client using Constructor Injection
class UserService {
    shared_ptr<NotificationService> notifier;
public:
    explicit UserService(shared_ptr<NotificationService> n) : notifier(move(n)) {}
    void registerUser() { notifier->send("Welcome!"); }
};

// 4. Composition Root (main)
int main() {
    auto emailSvc = make_shared<EmailService>();
    auto userSvc = make_shared<UserService>(emailSvc); // Injection happens here!
    userSvc->registerUser();
}

🚦 When to use (and NOT use) DI

✅ USE Dependency Injection when:

  • Classes use new for internal collaborators.
  • You have trouble mocking services in unit tests.
  • Your code is full of if/switch statements to select service behaviors.

❌ DO NOT use Dependency Injection when:

  • The class is tiny and has zero dependencies.
  • It is a static utility class (e.g., string formatting).
  • It is a one-off script where the overhead of abstraction is unjustified.

[!tip] Framework DI In enterprise C++ systems, manual injection gets tedious. Frameworks like Google Fruit or Boost.DI can automate the wiring of dependencies, making scalable DI effortless.
