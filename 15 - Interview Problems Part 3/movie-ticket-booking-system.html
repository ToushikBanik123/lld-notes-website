Designing a Movie Ticket Booking System (BookMyShow)

lldbook-my-showconcurrencylocks

📌 Designing a Movie Ticket Booking System

[!info] Navigation Module: [[15 - Interview Problems Part 3/index|← Interview Problems Part 3 Overview]]

🎯 Step 1: Clarify Requirements

Functional Requirements

  1. Discovery: Users can browse Movies, Theaters, and Shows.
  2. Booking: Users select a Show, view seat arrangement, and book specific seats.
  3. Payments: Payment confirmation marks seats as BOOKED.
  4. Admin: Theater admins manage shows and seating.

Non-Functional Requirements

  1. Concurrency (CRITICAL): Multiple users trying to book the exact same seat simultaneously must be handled safely. No double booking.
  2. Data Consistency: Seats should be locked temporarily during the payment process.
  3. Scalability: System handles massive spikes during blockbuster movie releases.

🧱 Step 2: Identify Core Entities

  1. Movie: ID, Title, Duration.
  2. Theater: Contains multiple Screens.
  3. Show: Links a Movie, Theater, StartTime, and a Map of Seats.
  4. Seat: ID, Type (Normal, Premium), Status (AVAILABLE, LOCKED, BOOKED).
  5. Booking: Ties User, Show, Seats, and PaymentStatus.

⚙️ Step 3: Architecture & Design Patterns

  1. Concurrency Control (Distributed Lock / ConcurrentHashMap):
    • A naive approach allows two users to read status == AVAILABLE and both proceed to payment.
    • We must introduce a LOCKED state. When User A initiates checkout, the seats become LOCKED for 10 minutes. User B sees them as unavailable. If User A's payment fails, a background cron job reverts the seats to AVAILABLE.
  2. Singleton Pattern: The central MovieTicketBookingSystem acts as the facade.

💻 Step 4: Core Implementation (C++)

cpp
#include <iostream>
#include <string>
#include <vector>
#include <unordered_map>
#include <mutex>
#include <stdexcept>

using namespace std;

// 1. Enums & Entities
enum class SeatStatus { AVAILABLE, LOCKED, BOOKED };

struct Seat {
    string id;
    int price;
    SeatStatus status = SeatStatus::AVAILABLE;
};

class Show {
public:
    string showId;
    string movieId;
    unordered_map<string, Seat> seats;
    mutex showMutex; // Local lock for concurrent access

    Show(string id, string mId) : showId(id), movieId(mId) {}
};

// 2. Booking Service
class BookingService {
public:
    string reserveSeats(Show& show, vector<string> seatIds, string userId) {
        lock_guard<mutex> lock(show.showMutex); // Critical section

        // 1. Validation Phase
        for (const string& sId : seatIds) {
            if (show.seats[sId].status != SeatStatus::AVAILABLE) {
                throw runtime_error("Seat " + sId + " is no longer available.");
            }
        }

        // 2. Lock Phase (Temporary hold before payment)
        int totalAmount = 0;
        for (const string& sId : seatIds) {
            show.seats[sId].status = SeatStatus::LOCKED;
            totalAmount += show.seats[sId].price;
        }

        string bookingId = "BKG_" + to_string(rand());
        cout << "User " << userId << " reserved seats. Booking ID: " << bookingId << " Total: $" << totalAmount << endl;
        return bookingId;
    }

    void confirmBooking(Show& show, vector<string> seatIds, string bookingId) {
        lock_guard<mutex> lock(show.showMutex);
        for (const string& sId : seatIds) {
            show.seats[sId].status = SeatStatus::BOOKED;
        }
        cout << "Booking " << bookingId << " confirmed!" << endl;
    }
};

int main() {
    Show show("SHOW_1", "AVENGERS_1");
    show.seats["A1"] = {"A1", 15};
    show.seats["A2"] = {"A2", 15};
    
    BookingService bs;

    try {
        // User 1 tries to reserve A1 and A2
        string bId = bs.reserveSeats(show, {"A1", "A2"}, "USER_1");
        
        // Simulating Payment Success
        bs.confirmBooking(show, {"A1", "A2"}, bId);

        // User 2 tries to reserve A1
        bs.reserveSeats(show, {"A1"}, "USER_2"); // Will throw error
    } catch(const exception& e) {
        cout << "Error: " << e.what() << endl;
    }

    return 0;
}

🚨 Edge Cases Handled

  • Double Booking Race Condition: The showMutex guarantees that the validation and the locking of seats are atomic. User 2 cannot sneak in between User 1's validation and lock.
  • Seat Lock Timeouts: In a real-world system, seats marked as LOCKED would have a Redis TTL. If the payment webhook isn't received in 10 minutes, the lock expires and the seats revert to AVAILABLE.
