📌 Designing a Digital Wallet System

[!info] Navigation Module: [[15 - Interview Problems Part 3/index|← Interview Problems Part 3 Overview]] Next: [[15 - Interview Problems Part 3/elevator-system|Designing an Elevator System →]]

🎯 Step 1: Clarify Requirements

Functional Requirements

  1. Wallets: Users have wallets with generated account numbers.
  2. Operations: Support Transfers, Deposits (via Payment Gateway), Withdrawals.
  3. Statements: Fetch transaction history based on date ranges.
  4. Constraints: Non-negative balance. Positive transaction amounts.

Non-Functional Requirements

  1. Concurrency (CRITICAL): Multiple concurrent transfers involving the same wallet must not corrupt the balance.
  2. Idempotency: Deposit callbacks from external gateways must be idempotent to prevent double-crediting.
  3. Precision: Store money using long long (minor units/cents), never floating-point.

🧱 Step 2: Identify Core Entities

  1. Wallet: ID, AccountNumber, BalanceMinor (long long), Status (ACTIVE, SUSPENDED).
  2. Transaction: FromWalletId, ToWalletId, Amount, Status (PENDING, COMPLETED, FAILED), Type (TRANSFER, DEPOSIT, WITHDRAWAL).
  3. PaymentGatewayProvider: Interface for external payments.

⚙️ Step 3: Concurrency & Lock Strategy

The biggest challenge in a Wallet LLD is deadlocks. If Wallet A transfers to Wallet B, and Wallet B transfers to Wallet A simultaneously, naive locking causes a deadlock.

Solution: Lexicographical Lock Ordering Always sort the lock keys before acquiring them.

cpp
string firstLock = min(fromId, toId);
string secondLock = max(fromId, toId);

lockService.acquire(firstLock);
lockService.acquire(secondLock);
// Perform transfer...

💻 Step 4: Core Implementation (C++)

cpp
#include <iostream>
#include <string>
#include <unordered_map>
#include <mutex>
#include <stdexcept>
#include <memory>

using namespace std;

// 1. Entities
struct Wallet {
    string id;
    long long balanceMinor;
    bool isActive;
};

// 2. Lock Service
class LockService {
    unordered_map<string, shared_ptr<mutex>> locks;
    mutex globalMtx;
public:
    shared_ptr<mutex> getLock(const string& key) {
        lock_guard<mutex> g(globalMtx);
        if (!locks[key]) locks[key] = make_shared<mutex>();
        return locks[key];
    }
};

// 3. Wallet Service
class WalletService {
    unordered_map<string, Wallet> db;
    LockService lockService;

public:
    WalletService() {
        db["W1"] = {"W1", 5000, true}; // $50.00
        db["W2"] = {"W2", 1000, true}; // $10.00
    }

    void transfer(string fromId, string toId, long long amount) {
        if (amount <= 0) throw runtime_error("Invalid amount");
        if (fromId == toId) throw runtime_error("Self transfer not allowed");

        // Deadlock Prevention: Sort keys
        string lock1 = min(fromId, toId);
        string lock2 = max(fromId, toId);

        auto mtx1 = lockService.getLock(lock1);
        auto mtx2 = lockService.getLock(lock2);

        // Acquire strictly in sorted order
        scoped_lock locks(*mtx1, *mtx2); 

        // Re-fetch state under lock
        Wallet& wFrom = db[fromId];
        Wallet& wTo = db[toId];

        if (!wFrom.isActive || !wTo.isActive) throw runtime_error("Wallet inactive");
        if (wFrom.balanceMinor < amount) throw runtime_error("Insufficient funds");

        // Mutate
        wFrom.balanceMinor -= amount;
        wTo.balanceMinor += amount;

        cout << "Transfer Success! " << fromId << " -> " << toId << " : " << amount << endl;
    }
};

int main() {
    WalletService svc;
    svc.transfer("W1", "W2", 1500); // Transfers $15.00
    return 0;
}

🚨 Edge Cases Handled

  • Idempotency in Callbacks: When the PaymentGateway triggers handleDepositCallback(transactionId), the service first checks if tx.status == COMPLETED. If it is, it returns immediately instead of crediting the wallet twice.
  • Deadlocks: A strictly ordered lock acquisition guarantees no circular waiting.
