📌 Builder Pattern

🎯 What is the Builder Pattern?

The Builder Pattern separates the construction of a complex object from its representation, allowing you to build objects step-by-step.

[!example] Real-World Analogy 🍔 Imagine ordering a custom burger. You choose the bun, patty, toppings, sauces, and whether you want it toasted. The chef follows your instructions step-by-step. This gives you total control over the final product without needing 100 different pre-set menu items.

⚠️ The Problem: Telescoping Constructors

Imagine building a BurgerMeal. It has mandatory components (Bun, Patty) and many optional ones (Cheese, Toppings, Side, Drink).

Without Builder, you often see the Telescoping Constructor Anti-Pattern:

cpp
// ❌ BAD PRACTICE — Telescoping Constructors
class BurgerMeal {
public:
    BurgerMeal(string bun, string patty);
    BurgerMeal(string bun, string patty, bool cheese);
    BurgerMeal(string bun, string patty, bool cheese, string side);
    BurgerMeal(string bun, string patty, bool cheese, string side, string drink);
};

Or a giant constructor where you have to pass empty placeholders:

cpp
// Hard to read, easy to mess up parameter order!
BurgerMeal plainBurger("wheat", "veg", false, {}, "", "");

🛠️ The Solution: The Builder

We create a nested Builder class that holds the configuration state, and a build() method to finally instantiate the immutable object.

1. The Immutable Product & Builder Class

cpp
class BurgerMeal {
    // 1. Immutable Fields (const)
    const string bunType;
    const string patty;
    const bool hasCheese;
    const string drink;

    // 2. Private Constructor (Forces use of Builder)
    BurgerMeal(string bun, string pat, bool cheese, string dr)
        : bunType(bun), patty(pat), hasCheese(cheese), drink(dr) {}

public:
    // 3. The Builder Class
    class Builder {
        string bunType;
        string patty;
        bool hasCheese = false; // defaults
        string drink = "None";

    public:
        // Mandatory fields in Builder constructor
        Builder(string bun, string pat) : bunType(bun), patty(pat) {}

        // Fluent API for optional fields (returns *this)
        Builder& withCheese(bool cheese) {
            hasCheese = cheese;
            return *this;
        }

        Builder& withDrink(string dr) {
            drink = dr;
            return *this;
        }

        // The final build step
        BurgerMeal build() const {
            if (bunType.empty() || patty.empty()) {
                throw runtime_error("Bun and Patty are mandatory!");
            }
            return BurgerMeal(bunType, patty, hasCheese, drink);
        }
    };
    
    void print() const {
        cout << "Burger: " << bunType << ", " << patty << ". Cheese: " << hasCheese << ". Drink: " << drink << "\n";
    }
};

2. Client Code (Fluent Chaining)

cpp
int main() {
    // Elegant, readable, step-by-step construction
    BurgerMeal myMeal = BurgerMeal::Builder("wheat", "chicken")
                            .withCheese(true)
                            .withDrink("Coke")
                            .build(); // Finalizes the immutable object
                            
    myMeal.print();
}

✅ Pros and Cons

ProsCons
Highly Readable: Fluent API (.withCheese().withDrink()) acts like named parametersBoilerplate: Requires creating a whole separate Builder class
Immutability: The final object can be completely constTwo-step creation: Object isn't ready until build() is called
Validation: Complex validation logic can live cleanly inside build()Overkill for simple objects

[!quote] Key Takeaway Use the Builder Pattern when constructing an object requires passing many parameters (especially optional ones) and you want to ensure the final constructed object is immutable and perfectly valid.
