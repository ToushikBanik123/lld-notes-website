📌 Singleton Design Pattern

🎯 What is the Singleton Pattern?

The Singleton Pattern ensures that a class has only one instance and provides a global point of access to that instance.

[!example] Real-World Analogy 🖨️ Think of an office Print Spooler. If 50 computers tried to talk to the printer directly at the same time, prints would overlap and crash. Instead, all print jobs go through one centralized Print Spooler service. There is only ever one spooler managing the queue.

When to use it?

  • Managing a Database Connection Pool
  • Logging Services
  • Application Configuration Settings
  • Hardware Interface Access

⚙️ How it Works

A typical Singleton involves three steps:

  1. Private constructor: Prevents new Singleton() from outside.
  2. Static variable: Holds the single instance.
  3. Public static method: getInstance() returns the instance.

1. Eager Loading (Early Initialization)

The instance is created as soon as the class is loaded.

Analogy: A fire extinguisher. It's always there, even if there's never a fire.

cpp
class EagerSingleton {
private:
    static EagerSingleton instance;
    EagerSingleton() {} // Private constructor

public:
    // Delete copy/assignment to prevent clones
    EagerSingleton(const EagerSingleton&) = delete;
    EagerSingleton& operator=(const EagerSingleton&) = delete;

    static EagerSingleton& getInstance() {
        return instance;
    }
};

// Created immediately at program startup
EagerSingleton EagerSingleton::instance;

Pros: 100% Thread-safe by default. Simple. Cons: Wastes memory if the instance is never actually used during the app's lifecycle.

2. Lazy Loading (On-Demand Initialization)

The instance is created only when getInstance() is called for the very first time.

Analogy: A coffee machine. It only brews coffee when you press the button, saving energy until needed.

cpp
class LazySingleton {
private:
    static LazySingleton* instance;
    LazySingleton() {}

public:
    LazySingleton(const LazySingleton&) = delete;
    LazySingleton& operator=(const LazySingleton&) = delete;

    static LazySingleton* getInstance() {
        if (instance == nullptr) {
            instance = new LazySingleton(); // Created on demand
        }
        return instance;
    }
};

LazySingleton* LazySingleton::instance = nullptr;

[!warning] The Threat to Lazy Loading The code above is NOT thread-safe! If Thread A and Thread B call getInstance() at the exact same millisecond, they both see instance == nullptr and both create an object. You now have TWO singletons! 💥

🛡️ Thread-Safe Singleton (Double-Checked Locking)

To fix the threading issue in Lazy Loading, we use a Mutex (Lock). But to avoid performance hits, we use the Double-Checked Locking pattern.

cpp
#include <mutex>

class ThreadSafeSingleton {
private:
    static ThreadSafeSingleton* instance;
    static std::mutex mtx; // The lock
    ThreadSafeSingleton() {}

public:
    ThreadSafeSingleton(const ThreadSafeSingleton&) = delete;
    ThreadSafeSingleton& operator=(const ThreadSafeSingleton&) = delete;

    static ThreadSafeSingleton* getInstance() {
        if (instance == nullptr) {            // Check 1 (No lock, fast)
            std::lock_guard<std::mutex> lock(mtx);
            if (instance == nullptr) {        // Check 2 (Locked, safe)
                instance = new ThreadSafeSingleton();
            }
        }
        return instance;
    }
};

ThreadSafeSingleton* ThreadSafeSingleton::instance = nullptr;
std::mutex ThreadSafeSingleton::mtx;

Why two checks?

  1. First check avoids the slow mutex lock if the object already exists (99% of the time).
  2. Second check ensures that if two threads passed the first check simultaneously, the second thread sees the object created by the first thread after acquiring the lock.

✅ Quick Revision

ApproachThread-Safe?Memory Efficient?Best For
Eager✅ Yes (Default)❌ No (Loads upfront)Light objects, guaranteed usage
Lazy (Basic)❌ No✅ YesSingle-threaded apps

[!quote] Key Takeaway Singleton provides global access to a single instance. Eager loading is easiest, but for multi-threaded apps where you want to save memory, use Lazy Loading with Double-Checked Locking.
