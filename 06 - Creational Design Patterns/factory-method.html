🎯 What is the Factory Method Pattern?

The Factory Pattern provides an interface for creating objects in a superclass, but allows subclasses to alter the type of objects that will be created.

Instead of calling a constructor directly (new Object()), we use a factory method to create the object based on some input or condition.

[!example] Real-World Analogy 🍕 Imagine you walk into a pizza shop and say, "I'd like a pizza." The shop doesn't ask you to go into the kitchen and make it. Instead, they ask, "Which type? Margherita? Pepperoni?" Based on your choice, the kitchen (factory) creates the specific pizza and hands it to you. You (the client) don't care how it's made, you just want your pizza.

⚠️ The Problem Without Factory

Let's say we have a Logistics app that handles "Air" and "Road" transport.

cpp
// ❌ BAD PRACTICE — Tightly Coupled
class LogisticsService {
public:
    void send(const string& mode) {
        if (mode == "Air") {
            Air* a = new Air();
            a->send();
            delete a;
        } else if (mode == "Road") {
            Road* r = new Road();
            r->send();
            delete r;
        }
    }
};

[!warning] Issues

  • Violates Open/Closed Principle (OCP): If we add "Ship", we MUST modify this send() method.
  • Tight Coupling: The service directly depends on concrete classes (Air, Road).

🛠️ The Solution: Factory Method

We move the object creation logic out of the business logic and into a dedicated Factory class.

cpp
// 1. Product Interface
class Logistics {
public:
    virtual void send() = 0;
    virtual ~Logistics() {}
};

// 2. Concrete Products
class Road : public Logistics {
public:
    void send() override { cout << "Sending by road 🚛\n"; }
};

class Air : public Logistics {
public:
    void send() override { cout << "Sending by air ✈️\n"; }
};

// 3. Factory Class
class LogisticsFactory {
public:
    static Logistics* getLogistics(const string& mode) {
        if (mode == "Air") return new Air();
        if (mode == "Road") return new Road();
        return nullptr;
    }
};

// 4. Client (Business Logic)
class LogisticsService {
public:
    void send(const string& mode) {
        // Business logic is fully decoupled from object creation!
        Logistics* logistics = LogisticsFactory::getLogistics(mode);
        if (logistics) {
            logistics->send();
            delete logistics;
        }
    }
};

✅ Pros and Cons

ProsCons
Loose Coupling: Client depends on interface, not concrete classComplexity: Requires extra classes/interfaces
OCP Compliant: Add new products without changing client codeOverkill for simple objects
SRP Compliant: Creation logic is centralized in one place

[!quote] Key Takeaway Use the Factory Pattern when your code needs to work with multiple types of objects that share a common interface, and the decision of which object to instantiate happens at runtime based on input.
