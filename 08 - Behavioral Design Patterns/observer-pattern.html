📌 Observer Pattern

🎯 What is the Observer Pattern?

The Observer Pattern defines a one-to-many relationship between objects so that when one object (the Subject or Publisher) changes state, all its dependents (the Observers or Subscribers) are notified and updated automatically.

It is heavily used in Event-Driven architectures, UI frameworks (Listeners), and publish-subscribe systems.

[!example] Real-World Analogy 🔔 Think of YouTube Subscriptions. The YouTube Channel is the Subject. You, the viewer, are the Observer. Instead of you constantly checking the channel page every 5 minutes to see if a new video is out (Polling), you click "Subscribe". When a new video drops, YouTube pushes a notification to you and millions of other subscribers automatically.

⚠️ The Problem: Tight Coupling & Polling

Imagine building a YouTube notification system. A naive approach hardcodes the notification logic inside the channel.

cpp
// ❌ BAD PRACTICE: Tight Coupling
class YouTubeChannel {
public:
    void uploadVideo(string title) {
        cout << "Uploaded: " << title << "\n";
        
        // HARDCODED NOTIFICATIONS! 
        // If we add SMS notifications tomorrow, we have to edit this class.
        sendEmail("user@example.com", title);
        sendAppPush("user2", title);
    }
};

This violates the Open-Closed Principle and Single Responsibility Principle. The Channel shouldn't care how users are notified, just that an event happened.

🛠️ The Solution: Subjects and Observers

We define interfaces for the Subject (which manages a list of observers) and the Observer (which has an update() method).

1. The Interfaces

cpp
class Subscriber { // Observer Interface
public:
    virtual ~Subscriber() = default;
    virtual void update(const string& videoTitle) = 0;
};

class Channel { // Subject Interface
public:
    virtual ~Channel() = default;
    virtual void subscribe(shared_ptr<Subscriber> s) = 0;
    virtual void unsubscribe(shared_ptr<Subscriber> s) = 0;
    virtual void notifySubscribers(const string& videoTitle) = 0;
};

2. Concrete Observers

cpp
class EmailSubscriber : public Subscriber {
private:
    string email;
public:
    EmailSubscriber(string e) : email(e) {}
    void update(const string& videoTitle) override {
        cout << "Email sent to " << email << ": New video - " << videoTitle << "\n";
    }
};

class MobileAppSubscriber : public Subscriber {
private:
    string username;
public:
    MobileAppSubscriber(string u) : username(u) {}
    void update(const string& videoTitle) override {
        cout << "App Push for " << username << ": New video - " << videoTitle << "\n";
    }
};

3. Concrete Subject

[!warning] C++ Best Practice: Use weak_ptr for Observers If the Subject holds shared_ptr to the Observers, it will keep them alive forever, causing a memory leak. The Subject should hold weak_ptr to loosely reference the Observers.

cpp
#include <vector>
#include <memory>
#include <algorithm>

class YouTubeChannel : public Channel {
private:
    vector<weak_ptr<Subscriber>> subscribers; // Weak references!
    string channelName;

    // Helper to remove destroyed observers
    void cleanup() {
        subscribers.erase(
            remove_if(subscribers.begin(), subscribers.end(),
                      [](const weak_ptr<Subscriber>& w) { return w.expired(); }),
            subscribers.end());
    }

public:
    YouTubeChannel(string name) : channelName(name) {}

    void subscribe(shared_ptr<Subscriber> s) override {
        cleanup();
        subscribers.push_back(s);
    }

    void unsubscribe(shared_ptr<Subscriber> s) override {
        subscribers.erase(
            remove_if(subscribers.begin(), subscribers.end(),
                      [&](const weak_ptr<Subscriber>& w) {
                          auto locked = w.lock();
                          return !locked || locked.get() == s.get();
                      }),
            subscribers.end());
    }

    void notifySubscribers(const string& videoTitle) override {
        cleanup();
        for (auto& w : subscribers) {
            if (auto s = w.lock()) { // Promote to shared_ptr temporarily
                s->update(videoTitle); // Fire the event!
            }
        }
    }

    // The actual business logic
    void uploadVideo(string title) {
        cout << "\n[" << channelName << " uploaded: " << title << "]\n";
        notifySubscribers(title);
    }
};

4. Client Code

cpp
int main() {
    YouTubeChannel tuf("takeUforward");

    auto emailUser = make_shared<EmailSubscriber>("rahul@example.com");
    auto appUser = make_shared<MobileAppSubscriber>("raj");

    tuf.subscribe(emailUser);
    tuf.subscribe(appUser);

    tuf.uploadVideo("Observer Pattern in C++"); 
    // Both users instantly get notified!
}

✅ Pros and Cons

ProsCons
Loose Coupling: Subject doesn't know the concrete classes of ObserversUnexpected Updates: Observers don't know about each other; a cascade of updates can cause performance issues
OCP: You can add new Observer types without changing the SubjectMemory Leaks (Lapsed Listener): Forgetting to unsubscribe in unmanaged languages leads to ghost objects
Dynamic Relationships: Can attach/detach observers at runtimeOrder is arbitrary: You cannot easily guarantee the order in which observers are notified

[!quote] Key Takeaway Use the Observer pattern when a change to one object requires changing others, and you don't know beforehand how many objects need to be changed (e.g., MVC architecture where Model updates notify Views).
