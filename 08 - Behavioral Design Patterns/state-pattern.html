📌 State Pattern

[!info] Navigation Module: [[00 - Course Overview/index|← Course Overview]] Prev: [[08 - Behavioral Design Patterns/observer-pattern|← Observer Pattern]] Next: TBD

🎯 What is the State Pattern?

The State Pattern encapsulates state-specific behavior into separate classes and delegates the behavior to the appropriate state object.

This allows an object to alter its behavior when its internal state changes. It appears as if the object has changed its entire class.

[!example] Real-World Analogy 🍔 Think of a Food Delivery App (like Swiggy/UberEats). An Order moves through states: Placed -> Preparing -> Out for Delivery -> Delivered. Your app's "Cancel" button behaves differently depending on the state:

  • If Placed or Preparing, clicking Cancel gives you a refund.
  • If Out for Delivery, clicking Cancel tells you "Cannot cancel, food is on the way". Instead of writing giant if-else blocks for the Cancel button, we put that logic into State classes.

⚠️ The Problem: Giant Switch/Case Statements

If we implement the state logic directly inside the main Order class, we end up with nasty conditional logic that violates the Open-Closed Principle.

cpp
// ❌ BAD PRACTICE: Spagetti Conditionals
class Order {
    string state = "ORDER_PLACED";
public:
    void cancelOrder() {
        if (state == "ORDER_PLACED" || state == "PREPARING") {
            state = "CANCELLED";
            cout << "Order cancelled.\n";
        } else if (state == "OUT_FOR_DELIVERY") {
            cout << "Too late to cancel!\n";
        } else if (state == "DELIVERED") {
            cout << "Already eaten!\n";
        }
    }
    
    void nextState() {
        // Another massive switch statement here...
    }
};

If we add a new state (e.g., PAYMENT_PENDING), we have to hunt down every single method in the class and add a new if statement.

🛠️ The Solution: State Classes

We define a State interface containing methods for all possible actions. Then, we create Concrete State classes (OrderPlacedState, OutForDeliveryState, etc.). The main OrderContext class just holds a pointer to the current State object and delegates actions to it.

1. The State Interface

cpp
class OrderContext; // Forward declaration

class OrderState {
public:
    virtual ~OrderState() = default;
    virtual void next(OrderContext* context) = 0;
    virtual void cancel(OrderContext* context) = 0;
    virtual string getStateName() = 0;
};

2. The Context (The Order)

The Context exposes the same interface, but passes the 'this' pointer to the current state so the state can change the Context's current state.

cpp
class OrderContext {
private:
    OrderState* currentState;

public:
    OrderContext(OrderState* initial) : currentState(initial) {}

    void setState(OrderState* state) {
        delete currentState; // Clean up old state (if managing memory manually)
        currentState = state;
    }

    void next() { currentState->next(this); }
    void cancel() { currentState->cancel(this); }
    string getStateName() { return currentState->getStateName(); }
};

3. Concrete States

Notice how the states themselves are responsible for triggering transitions by calling context->setState(...).

cpp
// --- Forward declarations of future states ---
class CancelledState;
class PreparingState;

// --- Order Placed State ---
class OrderPlacedState : public OrderState {
public:
    void next(OrderContext* context) override; // See impl below
    void cancel(OrderContext* context) override; 
    string getStateName() override { return "ORDER_PLACED"; }
};

// --- Out For Delivery State ---
class OutForDeliveryState : public OrderState {
public:
    void next(OrderContext* context) override {
        // context->setState(new DeliveredState());
        cout << "Transitioning to Delivered.\n";
    }
    void cancel(OrderContext* context) override {
        cout << "ERROR: Cannot cancel, food is out for delivery!\n";
    }
    string getStateName() override { return "OUT_FOR_DELIVERY"; }
};

// ... Imagine PreparingState, DeliveredState, CancelledState implemented here ...

4. Client Code

cpp
int main() {
    // Starts in "Placed" state
    OrderContext order(new OrderPlacedState()); 
    
    order.cancel(); // Successfully cancels the order
    
    // If order was in "OutForDeliveryState", calling order.cancel() 
    // would run the ERROR logic without a single if-else statement in the client!
}

⚖️ State vs. Strategy Pattern

These two patterns look identical in UML (both use composition to delegate behavior), but their intent is different:

AspectState PatternStrategy Pattern
IntentObject changes its behavior based on internal state changesObject lets client choose an algorithm at runtime
TransitionsStates know about each other and trigger transitionsStrategies are completely independent of each other
ExampleVending Machine, Order Tracking FSMSorting Algorithms, Payment Methods (Credit Card, PayPal)

✅ Pros and Cons

ProsCons
SRP: Organizes code related to specific states into separate classesOverkill for simple FSMs: If you only have 2 states that rarely change, simple if statements are better
OCP: Introduce new states without changing existing state classes or the contextClass Explosion: A complex Finite State Machine (FSM) will result in dozens of tiny classes
No more if-else: Eliminates bulky switch-case statements

[!quote] Key Takeaway Use the State pattern when you have an object that behaves differently depending on its current state, the number of states is large, and the state-specific code frequently changes. It is essentially an object-oriented way to build a Finite State Machine (FSM).
