📌 Visitor Pattern

🎯 What is the Visitor Pattern?

The Visitor Pattern allows you to add new operations or behaviors to a complex hierarchy of objects without modifying the objects themselves.

It achieves this by moving the operational logic out of the data classes and into a separate "Visitor" class.

[!example] Real-World Analogy 🚕 Think of an Insurance Agent (The Visitor). An insurance agent visits different places (Elements) like a House, a Bank, and a Coffee Shop.

  • At the House, the agent offers Medical & Home Insurance.
  • At the Bank, the agent offers Theft Insurance.
  • At the Coffee Shop, the agent offers Fire Insurance. The buildings don't need to know how to sell insurance. They just need to "open the door" (accept) the agent, and the agent performs the specific logic for that building type.

⚠️ The Problem: Polluting the Data Classes

Imagine an E-Commerce system with a shopping cart containing different items: PhysicalProduct, DigitalProduct, and GiftCard. We want to add an operation: "Calculate Shipping Cost".

cpp
// ❌ BAD PRACTICE: Polluting data classes with unrelated logic
class PhysicalProduct {
public:
    double calculateShipping() { return weight * 10; }
    void printInvoice() { /* logic */ } 
    // What if we want to add exportToXML() next week? We have to modify this class again!
};

Every time we want to perform a new operation (Calculate Taxes, Export to JSON, Generate Invoice) on the cart, we have to modify every single product class. This violates the Open-Closed Principle and bloats the data classes with unrelated logic.

🛠️ The Solution: Double Dispatch

We extract the operations into a Visitor interface. The product classes (Elements) implement an accept(Visitor) method. Inside this method, they call the visitor back, passing themselves as an argument. This is called Double Dispatch.

1. The Element and Visitor Interfaces

cpp
// Forward declarations
class PhysicalProduct;
class DigitalProduct;
class GiftCard;

// The Visitor Interface: Has an overloaded visit() method for EACH element type
class ItemVisitor {
public:
    virtual ~ItemVisitor() = default;
    virtual void visit(PhysicalProduct* item) = 0;
    virtual void visit(DigitalProduct* item) = 0;
    virtual void visit(GiftCard* item) = 0;
};

// The Element Interface
class Item {
public:
    virtual ~Item() = default;
    virtual void accept(ItemVisitor* visitor) = 0;
};

2. The Concrete Elements

The elements' only job is to route the visitor to the correct overloaded method based on their specific type (this).

cpp
class PhysicalProduct : public Item {
public:
    string name;
    double weight;
    PhysicalProduct(string n, double w) : name(n), weight(w) {}

    // Double Dispatch: The element tells the visitor exactly what type it is!
    void accept(ItemVisitor* visitor) override {
        visitor->visit(this); 
    }
};

class DigitalProduct : public Item {
public:
    string name;
    DigitalProduct(string n) : name(n) {}

    void accept(ItemVisitor* visitor) override {
        visitor->visit(this);
    }
};

class GiftCard : public Item {
public:
    string code;
    GiftCard(string c) : code(c) {}

    void accept(ItemVisitor* visitor) override {
        visitor->visit(this);
    }
};

3. The Concrete Visitors (The Operations)

Now, to add a new operation, we just create a new Visitor! We don't touch the Element classes at all.

cpp
class ShippingCostVisitor : public ItemVisitor {
public:
    void visit(PhysicalProduct* item) override {
        cout << "Shipping cost for " << item->name << " is $" << (item->weight * 10) << "\n";
    }

    void visit(DigitalProduct* item) override {
        cout << item->name << " is digital. No shipping cost.\n";
    }

    void visit(GiftCard* item) override {
        cout << "Gift card code sent via email. No shipping cost.\n";
    }
};

class JSONExportVisitor : public ItemVisitor {
public:
    void visit(PhysicalProduct* item) override {
        cout << "{ \"type\": \"Physical\", \"name\": \"" << item->name << "\" }\n";
    }
    void visit(DigitalProduct* item) override {
        cout << "{ \"type\": \"Digital\", \"name\": \"" << item->name << "\" }\n";
    }
    void visit(GiftCard* item) override {
        cout << "{ \"type\": \"GiftCard\", \"code\": \"" << item->code << "\" }\n";
    }
};

4. Client Code

cpp
#include <vector>

int main() {
    vector<Item*> cart = {
        new PhysicalProduct("Laptop", 2.5),
        new DigitalProduct("E-Book"),
        new GiftCard("AMZN-123")
    };

    ShippingCostVisitor shippingCalculator;
    JSONExportVisitor jsonExporter;

    // Apply the Shipping operation
    cout << "--- Shipping Calculation ---\n";
    for (auto item : cart) {
        item->accept(&shippingCalculator);
    }

    // Apply the JSON Export operation
    cout << "\n--- JSON Export ---\n";
    for (auto item : cart) {
        item->accept(&jsonExporter);
    }

    // Cleanup omitted for brevity
}

✅ Pros and Cons

ProsCons
OCP for Operations: You can add a new operation (Visitor) without modifying any element classesViolates OCP for Elements: If you add a new Element type (e.g., Subscription), you must update the Visitor interface and every single concrete visitor!
Separation of Concerns: Gathers related operations into a single class rather than spreading them across the data hierarchyDouble Dispatch Complexity: Tracing the execution flow (accept -> visit) can be confusing
Accumulate State: A visitor can accumulate state as it traverses a complex object structure (e.g., a total sum)Exposes Internals: Visitors often need public getters to access the elements' internal state

[!quote] Key Takeaway Use the Visitor pattern when you have a stable class hierarchy (the elements rarely change) but you frequently need to add new operations over that hierarchy (like Compilers running syntax checks, optimizations, and code generation over an Abstract Syntax Tree).
