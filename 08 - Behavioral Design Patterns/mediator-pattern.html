🎯 What is the Mediator Pattern?

The Mediator Pattern is a behavioral design pattern that centralizes complex communication between objects into a single mediation object.

Instead of objects communicating directly with each other (which leads to tightly coupled "spaghetti code"), they interact exclusively through the Mediator.

[!example] Real-World Analogy ✈️ Think of Air Traffic Control (ATC). Airplanes do not communicate directly with each other to decide who lands next. That would be chaotic and dangerous. Instead, every airplane communicates only with the ATC tower. The ATC tower holds the full picture and tells the planes what to do. The ATC is the Mediator.

⚠️ The Problem: Spaghetti Dependencies

Imagine a collaborative document editor like Google Docs. Users can give access to other users. If Alice makes a change, Bob and Charlie need to be notified.

cpp
// ❌ BAD PRACTICE: Tight Coupling & Spaghetti Code
class User {
public:
    string name;
    vector<User*> collaborators; // Every user holds pointers to everyone else!

    void makeChange(string change) {
        cout << name << " edited: " << change << "\n";
        for (User* u : collaborators) {
            u->receiveChange(change, this); // Direct communication
        }
    }
    // ...
};

Issues:

  1. Tight Coupling: Users are explicitly linked to other users.
  2. Scalability: As the system grows, managing who knows whom becomes a nightmare.
  3. SRP Violation: The User class manages both user-specific logic and collaboration/notification logic.

🛠️ The Solution: Centralized Mediator

We extract the communication logic into a new class called the Mediator (e.g., CollaborativeDocument). Now, the User objects only hold a reference to the Mediator. When a User makes a change, they tell the Mediator. The Mediator figures out who else needs to know.

1. The Mediator Interface

cpp
class User; // Forward declaration

class DocumentSessionMediator {
public:
    virtual ~DocumentSessionMediator() = default;
    virtual void join(User* user) = 0;
    virtual void broadcastChange(const string& change, User* sender) = 0;
};

2. The Colleague (User)

cpp
class User {
protected:
    string name;
    DocumentSessionMediator* mediator; // Only knows about the mediator!

public:
    User(string n, DocumentSessionMediator* m) : name(n), mediator(m) {}

    void makeChange(const string& change) {
        cout << name << " edited the document: " << change << "\n";
        mediator->broadcastChange(change, this); // Let the mediator handle it
    }

    void receiveChange(const string& change, User* sender) {
        // ... (called by the mediator)
    }
};

3. The Concrete Mediator

cpp
class CollaborativeDocument : public DocumentSessionMediator {
private:
    vector<User*> users; // The mediator tracks the users

public:
    void join(User* user) override {
        users.push_back(user);
    }

    void broadcastChange(const string& change, User* sender) override {
        // Send the change to everyone EXCEPT the person who made it
        for (User* user : users) {
            if (user != sender) {
                user->receiveChange(change, sender);
            }
        }
    }
};

4. Client Code

cpp
int main() {
    CollaborativeDocument doc; // The Central Mediator

    // Users are created pointing to the mediator
    User alice("Alice", &doc);
    User bob("Bob", &doc);
    User charlie("Charlie", &doc);

    doc.join(&alice); doc.join(&bob); doc.join(&charlie);

    // Alice doesn't know Bob or Charlie exist. She just talks to the doc.
    alice.makeChange("Added a title"); 
}

✅ Pros and Cons

ProsCons
Decoupling: Reduces chaotic dependencies from M:N to 1:NGod Object Risk: The mediator can easily bloat into a "God Object" that knows too much
SRP: Extracts communication logic into a single placeSingle Point of Failure: If the mediator crashes, all communication stops
Centralized Control: Easy to add new rules (e.g., muting a user, admin permissions) in one place

[!quote] Key Takeaway Use the Mediator pattern when you have a set of objects that communicate in complex, tightly coupled ways (like a complex UI dialog with many interacting form fields, or chat room architectures).
