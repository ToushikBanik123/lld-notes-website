📌 Chain of Responsibility Pattern

[!info] Navigation Module: [[00 - Course Overview/index|← Course Overview]] Prev: [[08 - Behavioral Design Patterns/overview|← Behavioral Patterns Intro]] Next: [[08 - Behavioral Design Patterns/command-pattern|Command Pattern →]]

🎯 What is the Chain of Responsibility Pattern?

The Chain of Responsibility pattern transforms behaviors into standalone objects called handlers. It allows a request to be passed along a chain of handlers until one of them processes it.

[!example] Real-World Analogy 🎧 Think of a Customer Support hotline. You call with an issue. First, a Level 1 (General) agent answers. If they can't solve it, they pass you to a Level 2 (Technical) agent. If it's a billing issue, they pass you to the Billing Department. The request travels down the chain until a handler can successfully resolve it.

⚠️ The Problem: Monolithic Routing

Imagine building a support ticket router. A naive implementation uses a giant if-else block:

cpp
// ❌ BAD PRACTICE: Tight Coupling & OCP Violation
class SupportService {
public:
    void handleRequest(const string& type) {
        if (type == "general") {
            cout << "Handled by General Support\n";
        } else if (type == "refund") {
            cout << "Handled by Billing Team\n";
        } else if (type == "technical") {
            cout << "Handled by Technical Support\n";
        } else {
            cout << "No handler available\n";
        }
    }
};

Every time a new department is added, you have to modify this class (violating the Open-Closed Principle). The order of processing is hardcoded, making it rigid.

🛠️ The Solution: Linked Handlers

We create an abstract SupportHandler class that holds a pointer to the next handler in the chain. Each concrete handler checks if it can process the request; if not, it forwards it to the next handler.

1. Abstract Handler

cpp
class SupportHandler {
protected:
    SupportHandler* nextHandler = nullptr;

public:
    virtual ~SupportHandler() = default;

    // Build the chain
    void setNextHandler(SupportHandler* next) {
        nextHandler = next;
    }

    virtual void handleRequest(const string& requestType) = 0;
};

2. Concrete Handlers

cpp
class GeneralSupport : public SupportHandler {
public:
    void handleRequest(const string& requestType) override {
        if (requestType == "general") {
            cout << "GeneralSupport: Handling general query\n";
        } else if (nextHandler != nullptr) {
            nextHandler->handleRequest(requestType); // Pass it down the chain
        }
    }
};

class BillingSupport : public SupportHandler {
public:
    void handleRequest(const string& requestType) override {
        if (requestType == "refund") {
            cout << "BillingSupport: Handling refund request\n";
        } else if (nextHandler != nullptr) {
            nextHandler->handleRequest(requestType);
        }
    }
};

class TechnicalSupport : public SupportHandler {
public:
    void handleRequest(const string& requestType) override {
        if (requestType == "technical") {
            cout << "TechnicalSupport: Handling technical issue\n";
        } else if (nextHandler != nullptr) {
            nextHandler->handleRequest(requestType);
        } else {
            cout << "Request dropped: No handler found.\n";
        }
    }
};

3. Client Code

cpp
int main() {
    // 1. Create Handlers
    SupportHandler* general = new GeneralSupport();
    SupportHandler* billing = new BillingSupport();
    SupportHandler* technical = new TechnicalSupport();

    // 2. Build the Chain: General -> Billing -> Technical
    general->setNextHandler(billing);
    billing->setNextHandler(technical);

    // 3. Send requests to the head of the chain
    general->handleRequest("refund");    // Handled by Billing
    general->handleRequest("technical"); // Handled by Technical
    general->handleRequest("unknown");   // Dropped

    delete general; delete billing; delete technical;
}

✅ Pros and Cons

ProsCons
Decoupling: Sender doesn't need to know which handler will process the requestDropped Requests: If the chain reaches the end without a match, the request goes unhandled
OCP Compliant: Easy to add or remove handlers without changing existing codeDebugging: Following execution flow through a long chain can be difficult
Dynamic Sequencing: You can change the order of handlers at runtimePerformance: Long chains might impact performance

[!quote] Key Takeaway Use the Chain of Responsibility when multiple objects can handle a request, but the specific handler is not known beforehand, and you want to decouple the sender from the receiver (e.g., UI Event bubbling, Middleware in web frameworks).
