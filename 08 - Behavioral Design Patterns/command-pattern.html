🎯 What is the Command Pattern?

The Command Pattern is a behavioral design pattern that encapsulates a request as an object.

This allows you to decouple the code that issues the request (Invoker) from the code that performs it (Receiver). Because the request is now an object, you can pass it around, queue it, log it, or undo it.

[!example] Real-World Analogy 📺 Think of a TV Remote Control. You press a button (Invoker). The button doesn't know how to turn on the TV, it just holds a "TurnOn" Command. The command knows how to talk to the TV (Receiver). Because the commands are separate objects, you can easily map any button to any command, or keep a history of pressed buttons to implement an "Undo" feature.

⚠️ The Problem: Hardcoded Logic

Imagine a simple Smart Home Remote. If we hardcode the logic into the remote buttons, the remote becomes tightly coupled to the devices (Light, AC).

cpp
// ❌ BAD PRACTICE: Tight Coupling
class NaiveRemoteControl {
    Light* light;
    AC* ac;
    string lastAction;
public:
    void pressLightOn() {
        light->on();
        lastAction = "LIGHT_ON";
    }
    // Hardcoded Undo logic is a nightmare to scale!
    void pressUndo() {
        if (lastAction == "LIGHT_ON") light->off();
        // ... 50 more if statements for every device
    }
};

If we add a Fan or a TV, we have to modify the Remote Control class. This violates OCP.

🛠️ The Solution: Command Objects

We define a Command interface. Concrete commands (e.g., LightOnCommand) implement this interface and hold a reference to the actual device (Receiver). The Remote (Invoker) only holds a list of Command objects.

1. The Receivers (The Devices)

cpp
class Light {
public:
    void on() { cout << "Light is ON\n"; }
    void off() { cout << "Light is OFF\n"; }
};

2. The Command Interface

cpp
class Command {
public:
    virtual ~Command() = default;
    virtual void execute() = 0;
    virtual void undo() = 0;
};

3. Concrete Commands

cpp
class LightOnCommand : public Command {
private:
    Light* light;
public:
    explicit LightOnCommand(Light* l) : light(l) {}
    
    void execute() override { light->on(); }
    void undo() override { light->off(); } // Built-in Undo!
};

class LightOffCommand : public Command {
private:
    Light* light;
public:
    explicit LightOffCommand(Light* l) : light(l) {}
    
    void execute() override { light->off(); }
    void undo() override { light->on(); }
};

4. The Invoker (The Remote Control)

cpp
#include <stack>

class RemoteControl {
private:
    Command* buttons[2]; // Slots for buttons
    stack<Command*> commandHistory;

public:
    void setCommand(int slot, Command* cmd) {
        buttons[slot] = cmd;
    }

    void pressButton(int slot) {
        if (buttons[slot] != nullptr) {
            buttons[slot]->execute();
            commandHistory.push(buttons[slot]); // Save for undo
        }
    }

    void pressUndo() {
        if (!commandHistory.empty()) {
            commandHistory.top()->undo();
            commandHistory.pop();
        }
    }
};

5. Client Code

cpp
int main() {
    Light myLight;
    
    Command* lightOn = new LightOnCommand(&myLight);
    Command* lightOff = new LightOffCommand(&myLight);

    RemoteControl remote;
    remote.setCommand(0, lightOn);
    remote.setCommand(1, lightOff);

    remote.pressButton(0); // Light ON
    remote.pressButton(1); // Light OFF
    remote.pressUndo();    // Undo -> Light ON
}

✅ Pros and Cons

ProsCons
Decoupling: Decouples the object that invokes the operation from the one that knows how to perform itClass Explosion: Can result in a massive number of small Command classes
Undo/Redo: Easy to implement robust Undo/Redo mechanisms using history stacksComplexity: Adds layers of indirection
Queuing: Commands can be queued, delayed, or serialized to disk

[!quote] Key Takeaway Use the Command Pattern when you need to parameterize objects with actions, queue operations, schedule execution, or support undoable operations (like text editors, remote controls, or game input systems).
