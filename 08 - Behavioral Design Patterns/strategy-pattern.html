🎯 What is the Strategy Pattern?

The Strategy Pattern is a behavioral design pattern that defines a family of algorithms, encapsulates each one into a separate class, and makes them interchangeable at runtime.

It allows the algorithm to vary independently from the clients that use it.

[!example] Real-World Analogy 🚗 Think of a Navigation App (like Google Maps). You want to get from Point A to Point B. The app can calculate the route using different strategies:

  • Driving Route (Fastest, avoids tolls)
  • Walking Route (Shortest path, uses sidewalks)
  • Cycling Route (Uses bike lanes) Instead of cramming all routing math into one giant Navigator class, each routing method is a separate Strategy class. You can switch between them seamlessly.

⚠️ The Problem: Monolithic Conditionals

Imagine an E-Commerce system that needs to calculate discounts. A naive approach puts all the logic into a massive if-else block.

cpp
// ❌ BAD PRACTICE: Hardcoded Algorithms
class Checkout {
public:
    double calculateTotal(double amount, const string& discountType) {
        if (discountType == "FESTIVAL") {
            return amount * 0.8; // 20% off
        } else if (discountType == "NEW_USER") {
            return amount * 0.9; // 10% off
        } else if (discountType == "VIP") {
            return amount * 0.7; // 30% off
        } else {
            return amount; 
        }
    }
};

This violates the Open-Closed Principle (OCP). If we add a FLAT_50 discount, we have to modify the Checkout class. It also makes the Checkout class difficult to test and maintain as the number of algorithms grows.

🛠️ The Solution: The Strategy Interface

We extract each discount algorithm into its own class implementing a common DiscountStrategy interface. The Checkout (Context) class only holds a pointer to the Strategy and delegates the calculation to it.

1. The Strategy Interface

cpp
class DiscountStrategy {
public:
    virtual ~DiscountStrategy() = default;
    virtual double calculate(double amount) = 0;
};

2. Concrete Strategies

cpp
class FestivalDiscount : public DiscountStrategy {
public:
    double calculate(double amount) override {
        return amount * 0.8; // 20% off
    }
};

class NewUserDiscount : public DiscountStrategy {
public:
    double calculate(double amount) override {
        return amount * 0.9; // 10% off
    }
};

class NoDiscount : public DiscountStrategy {
public:
    double calculate(double amount) override {
        return amount;
    }
};

3. The Context

The context maintains a reference to a Strategy object and allows clients to swap it at runtime.

cpp
#include <memory>
using namespace std;

class Checkout {
private:
    unique_ptr<DiscountStrategy> strategy; // Encapsulated algorithm

public:
    // Inject the initial strategy via constructor
    Checkout(unique_ptr<DiscountStrategy> initialStrategy) 
        : strategy(std::move(initialStrategy)) {}

    // Allow swapping strategy at runtime
    void setStrategy(unique_ptr<DiscountStrategy> newStrategy) {
        strategy = std::move(newStrategy);
    }

    // Delegate the work to the strategy
    double processPayment(double amount) {
        if (!strategy) return amount;
        return strategy->calculate(amount);
    }
};

4. Client Code

cpp
int main() {
    // 1. Start with New User Discount
    Checkout cart(make_unique<NewUserDiscount>());
    cout << "Total: " << cart.processPayment(100.0) << "\n"; // 90.0

    // 2. Switch to Festival Discount at runtime!
    cart.setStrategy(make_unique<FestivalDiscount>());
    cout << "Total: " << cart.processPayment(100.0) << "\n"; // 80.0
}

⚖️ Strategy vs. State Pattern

AspectStrategy PatternState Pattern
IntentProvide interchangeable algorithms to achieve a goalAllow an object to alter behavior when internal state changes
Who changes it?The Client passes the strategy to the ContextThe State objects themselves often trigger transitions to other states
DependenciesStrategies are completely independent of each otherStates often know about each other to transition between them

✅ Pros and Cons

ProsCons
OCP: Add new algorithms without changing the ContextClass Explosion: Can result in many small classes
Eliminates Conditionals: Replaces giant switch/case blocksClient Awareness: The client must understand the differences between the strategies to choose the right one
Composition over Inheritance: Context is not locked into a specific algorithm via subclassing

[!quote] Key Takeaway Use the Strategy pattern when you have multiple different ways (algorithms) to perform the exact same task (e.g., sorting, routing, compression, pricing), and you want to swap them at runtime without bloated if-else blocks.
