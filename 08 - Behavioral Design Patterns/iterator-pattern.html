📌 Iterator Pattern

🎯 What is the Iterator Pattern?

The Iterator Pattern provides a way to access the elements of an aggregate object (a collection) sequentially without exposing its underlying representation.

It extracts the traversal behavior of a collection into a separate object called an Iterator.

[!example] Real-World Analogy 🎧 Think of a Playlist on Spotify. You don't know or care if the songs are stored in an Array, a Linked List, or a Binary Tree on Spotify's servers. You just press the "Next" button to go to the next song. The Iterator acts as that "Next" button.

⚠️ The Problem: Exposing Internal Data Structures

Suppose you have a YouTubePlaylist class. If it exposes its internal std::vector directly so clients can loop over it, you break encapsulation.

cpp
// ❌ BAD PRACTICE: Breaks encapsulation
class YouTubePlaylist {
    vector<string> videos;
public:
    // Exposes the internal structure! If we change to std::list later, 
    // ALL client code breaks.
    const vector<string>& getVideos() const { return videos; } 
};

int main() {
    YouTubePlaylist playlist;
    // Client is tightly coupled to std::vector
    for (const auto& v : playlist.getVideos()) {
        cout << v << "\n";
    }
}

🛠️ The Solution: The Iterator Interface

We create an Iterator interface with methods like hasNext() and next(). The collection implements an Iterable interface that provides a method to create an iterator for itself.

1. Iterator and Iterable Interfaces

cpp
// Defines how to traverse
class Iterator {
public:
    virtual ~Iterator() = default;
    virtual bool hasNext() const = 0;
    virtual const string* next() = 0;
};

// Defines that the collection can be traversed
class Playlist {
public:
    virtual ~Playlist() = default;
    virtual unique_ptr<Iterator> createIterator() const = 0;
};

2. Concrete Iterator

This class understands how to traverse the specific internal structure (a vector in this case), but keeps that knowledge hidden from the client.

cpp
class YouTubePlaylistIterator : public Iterator {
private:
    const vector<string>& videos;
    size_t position = 0;

public:
    YouTubePlaylistIterator(const vector<string>& v) : videos(v) {}

    bool hasNext() const override {
        return position < videos.size();
    }

    const string* next() override {
        if (!hasNext()) return nullptr;
        return &videos[position++]; // Return current, then advance
    }
};

3. Concrete Collection

cpp
class YouTubePlaylist : public Playlist {
private:
    vector<string> videos; // Internal storage hidden!

public:
    void addVideo(const string& title) {
        videos.push_back(title);
    }

    // Returns the iterator, hiding the fact that 'videos' is a vector
    unique_ptr<Iterator> createIterator() const override {
        return make_unique<YouTubePlaylistIterator>(videos);
    }
};

4. Client Code

cpp
int main() {
    YouTubePlaylist playlist;
    playlist.addVideo("LLD Tutorial");
    playlist.addVideo("System Design Basics");

    // Client only interacts with the Iterator interface!
    unique_ptr<Iterator> it = playlist.createIterator();

    while (it->hasNext()) {
        cout << *(it->next()) << "\n";
    }
}

🧬 C++ STL Iterators

In the real world, C++ has this built right into the Standard Template Library (STL). Instead of hasNext() and next(), C++ uses begin(), end(), operator*, and operator++.

cpp
vector<int> nums = {1, 2, 3};
// Standard C++ Iterator Pattern
for (auto it = nums.begin(); it != nums.end(); ++it) {
    cout << *it << "\n";
}

// Range-based for-loop is just syntactic sugar over iterators!
for (int num : nums) {
    cout << num << "\n";
}

✅ Pros and Cons

ProsCons
Encapsulation: Hides the internal data structure from the clientOverkill for simple structures: Adding full iterator classes for simple arrays is verbose
Uniformity: Client uses the exact same while(hasNext) loop for Vectors, Trees, or GraphsIterator Invalidation: If the collection is modified while iterating, iterators can crash the program
Multiple Traversals: You can easily implement a ReverseIterator or have multiple active iterators

[!quote] Key Takeaway Use the Iterator pattern when your collection has a complex data structure under the hood (like a Tree or Graph), but you want clients to be able to iterate over its elements in a simple, standardized way.
