Overview

Software design principles are guidelines that help developers create systems that are easy to understand, maintain, and extend.

1. 🧱 DRY — Don't Repeat Yourself

[!tip] Definition Every piece of knowledge must have a single, unambiguous, authoritative representation within a system.

In simple terms: avoid duplication of logic or code. Repeating code makes the system hard to maintain and error-prone.

❌ Bad Code (Violates DRY)

cpp
#include <iostream>
using namespace std;

int main() {
    // Area calculation logic is DUPLICATED
    int length1 = 10, width1 = 5;
    int area1 = length1 * width1;
    cout << "Area1: " << area1 << endl;

    int length2 = 8, width2 = 4;
    int area2 = length2 * width2;       // ← Same logic repeated!
    cout << "Area2: " << area2 << endl;

    return 0;
}

✅ Good Code (Follows DRY)

cpp
#include <iostream>
using namespace std;

class AreaCalculator {
public:
    // Single source of truth for area logic
    static int calculateArea(int length, int width) {
        return length * width;
    }
};

int main() {
    int area1 = AreaCalculator::calculateArea(10, 5);
    int area2 = AreaCalculator::calculateArea(8, 4);

    cout << "Area1: " << area1 << endl;
    cout << "Area2: " << area2 << endl;
    return 0;
}

How to Apply DRY in Practice

  • Extract common functionality into methods or utility classes
  • Leverage libraries and frameworks when available
  • Refactor duplicate logic regularly across classes or layers

[!warning] When NOT to Use DRY

  • Premature Abstraction: Two blocks look similar now but may diverge later — extracting too early creates unnecessary coupling
  • Performance-Critical Code: Generalized methods may block compiler optimizations like inlining
  • Sacrificing Readability: If extracting makes code less readable, prefer clarity
  • Legacy Codebases: Don't refactor without tests — you might accidentally change behavior

2. 💋 KISS — Keep It Simple, Stupid

[!tip] Definition Simplicity should be a key goal in design. Avoid unnecessary complexity. Use the simplest solution that works.

❌ Bad Code (Over-engineered)

cpp
class NumberUtils {
public:
    static bool isEven(int number) {
        // Unnecessarily complex!
        bool isEven = false;
        if (number % 2 == 0) {
            isEven = true;
        } else {
            isEven = false;
        }
        return isEven;
    }
};

✅ Good Code (Simple and Clear)

cpp
class NumberUtils {
public:
    static bool isEven(int number) {
        return number % 2 == 0;  // One line. Done.
    }
};

Why Simplicity Wins

BenefitHow
Easier DebuggingLess code = fewer places bugs can hide
Improved ReadabilityNew team members can understand quickly
Better MaintainabilityChanges are easier to make and test
Faster DevelopmentLess time writing, more time shipping

3. 🚫 YAGNI — You Aren't Gonna Need It

[!tip] Definition Always implement things when you actually need them, never when you just foresee that you might need them.

The Trap

[!example] Scenario You're asked to build a note-taking app with Create and View features.

You start thinking: "What if later they want categories? Tagging? Google Drive sync? I should prepare for that!"

❌ This creates unnecessary complexity and wastes time. ✅ Build what's needed NOW. Add features when they're actually required.

Why YAGNI Matters

BenefitExplanation
Reduced WasteNo time spent on unused features
Simplified CodebaseLess code to maintain and debug
Faster DevelopmentFocus on what matters right now

[!warning] When NOT to Use YAGNI

  • Well-known requirements: If a feature is committed and coming in 2 sprints, designing for it now saves refactoring later
  • Performance-critical areas: Preemptively building for real-world usage patterns catches bottlenecks early
