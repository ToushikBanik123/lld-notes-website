🎯 What is the Proxy Pattern?

The Proxy Pattern provides a surrogate or placeholder for another object to control access to it.

A proxy implements the exact same interface as the real object, allowing it to intercept requests, perform additional logic (like caching, security checks, or lazy loading), and then pass the request to the real object.

[!example] Real-World Analogy 👔 Think of a busy CEO and their Personal Assistant. The CEO is the real object. The Assistant is the Proxy. If you want to talk to the CEO, you talk to the Assistant first. The Assistant filters spam, answers common questions from a cache, and only bothers the CEO if it's absolutely necessary.

⚠️ The Problem: Expensive Operations

Imagine a Video Downloader app. If a user clicks download on a 5GB video multiple times, downloading it over the network every single time wastes massive bandwidth and time.

cpp
// ❌ BAD PRACTICE: No caching, no access control
class RealVideoDownloader {
public:
    string download(const string& url) {
        cout << "Making heavy network call to: " << url << "\n";
        return "Video Data...";
    }
};

int main() {
    RealVideoDownloader downloader;
    downloader.download("youtube.com/video1");
    // Repeating the call repeats the heavy network request!
    downloader.download("youtube.com/video1"); 
}

🛠️ The Solution: The Proxy

We create an interface that both the Real object and the Proxy will implement. The Proxy handles the caching logic and only calls the Real object on a cache miss.

1. Subject Interface

cpp
class VideoDownloader {
public:
    virtual ~VideoDownloader() = default;
    virtual string download(const string& url) = 0;
};

2. The Real Subject

cpp
class RealVideoDownloader : public VideoDownloader {
public:
    string download(const string& url) override {
        cout << "[Network] Downloading video from: " << url << "\n";
        return "Video Data for " + url;
    }
};

3. The Proxy (Caching Proxy)

cpp
#include <unordered_map>
#include <memory>

class CachedVideoDownloader : public VideoDownloader {
private:
    unique_ptr<RealVideoDownloader> realDownloader;
    unordered_map<string, string> cache;

public:
    CachedVideoDownloader() {
        realDownloader = make_unique<RealVideoDownloader>();
    }

    string download(const string& url) override {
        // Intercept the request! Check cache first.
        if (cache.find(url) != cache.end()) {
            cout << "[Cache] Returning cached video for: " << url << "\n";
            return cache[url];
        }

        // Cache miss. Forward to real object.
        string data = realDownloader->download(url);
        cache[url] = data; // Store for next time
        return data;
    }
};

4. Client Code

cpp
int main() {
    // Client only knows about the interface
    unique_ptr<VideoDownloader> proxy = make_unique<CachedVideoDownloader>();

    // Triggers network call
    proxy->download("youtube.com/video1");

    // Intercepted! Served from cache instantly.
    proxy->download("youtube.com/video1"); 
}

🧩 Types of Proxies

  1. Virtual Proxy: Delays creation of a heavy object until it's actually needed (Lazy Loading).
  2. Protection Proxy: Checks if the client has permissions before forwarding the request to the real object.
  3. Remote Proxy: Represents an object located on a different server (e.g., gRPC stubs).
  4. Caching Proxy: Caches results of expensive operations (as seen in our example above).

✅ Pros and Cons

ProsCons
Control: Controls access to the real object without modifying it (OCP)Complexity: Introduces new classes and layers of indirection
Optimization: Great for lazy loading or cachingDelay: Might add a slight delay in response time due to the interception
Security: Great for adding protection/auth layers

[!quote] Key Takeaway Use the Proxy Pattern when you want to intercept and control access to an object. It's the perfect place to add caching, lazy initialization, or security checks without touching the real object's code.
