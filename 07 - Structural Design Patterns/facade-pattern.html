📌 Facade Pattern

🎯 What is the Facade Pattern?

The Facade Pattern provides a simplified, unified high-level interface to a complex subsystem or group of classes.

It acts as a single entry point for clients to interact with the system, hiding the underlying complexity and making the system easier to use.

[!example] Real-World Analogy 🚗 Think of driving a car. Manual Car (No Facade): You have to manually coordinate the clutch, gear shifter, and accelerator. It's complex and exposes all the inner workings to the driver. Automatic Car (Facade): You just select "Drive" and press the pedal. The complex gear-shifting mechanics are hidden behind a simple interface.

⚠️ The Problem: Client Complexity

Imagine booking a movie ticket. A robust system (like BookMyShow) has multiple microservices/subsystems: Payment, Seating, Notifications, Loyalty Points, and Ticketing.

If a client has to interact with all of them directly, the code becomes tightly coupled and complex:

cpp
// ❌ BAD PRACTICE: Client has to know about every service!
int main() {
    PaymentService payment;
    payment.makePayment("user123", 500);

    SeatReservationService seats;
    seats.reserveSeat("movie456", "A10");

    TicketService tickets;
    tickets.generateTicket("movie456", "A10");

    LoyaltyPointsService loyalty;
    loyalty.addPoints("user123", 50);

    NotificationService notifications;
    notifications.sendBookingConfirmation("user@example.com");
}

This violates the Single Responsibility Principle (the client knows too much) and causes duplicate code if you book tickets from multiple places (e.g., Web App, Mobile App).

🛠️ The Solution: The Facade

We create a single MovieBookingFacade class that encapsulates all these steps.

1. The Complex Subsystems

(Assume the classes from above: PaymentService, SeatReservationService, etc. exist).

2. The Facade Class

cpp
class MovieBookingFacade {
private:
    // The facade owns the workflow and coordinates all subsystems
    PaymentService paymentService;
    SeatReservationService seatReservationService;
    NotificationService notificationService;
    LoyaltyPointsService loyaltyPointsService;
    TicketService ticketService;

public:
    // Provides a simplified interface
    void bookMovieTicket(const string& userId, const string& movieId, 
                         const string& seatNum, const string& email, double amount) {
        
        paymentService.makePayment(userId, amount);
        seatReservationService.reserveSeat(movieId, seatNum);
        ticketService.generateTicket(movieId, seatNum);
        loyaltyPointsService.addPoints(userId, 50);
        notificationService.sendBookingConfirmation(email);

        cout << "Movie ticket booking completed successfully!\n";
    }
};

3. The Client

cpp
int main() {
    MovieBookingFacade facade;
    
    // Client only talks to the Facade!
    facade.bookMovieTicket("user123", "movie456", "A10", "user@example.com", 500);
}

✅ Pros and Cons

ProsCons
Lightweight Coupling: Reduces dependencies between client and subsystemsGod Object Risk: The facade can become a "god object" attached to all classes of an app if not careful
Simplifies Client Code: Client interacts with one easy APIHidden Complexity: The complexity is still there, just moved to the facade
Promotes Layered Architecture: Excellent for creating boundaries between application tiers

[!quote] Key Takeaway Use the Facade Pattern when you have a complex subsystem with dozens of classes, and you want to provide a straightforward, easy-to-use API for the most common tasks.
