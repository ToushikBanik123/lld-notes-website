📌 Adapter Pattern

🎯 What is the Adapter Pattern?

The Adapter Pattern allows incompatible interfaces to work together by acting as a translator or wrapper around an existing class.

It converts the interface of a class (the Adaptee) into another interface that a client expects (the Target).

[!example] Real-World Analogy 🔌 Imagine traveling from India to Europe. Your laptop charger has an Indian plug, but the hotel room only has European sockets. Instead of buying a new laptop or rewiring the hotel, you use a travel plug adapter. The adapter makes your charger compatible with the wall socket without modifying either.

⚠️ The Problem: Incompatible Interfaces

Suppose we have a CheckoutService that processes payments. It expects any payment provider to implement the standard PaymentGateway interface.

PayUGateway follows this interface perfectly. But we want to add RazorpayAPI, which is an external library and uses a different method name (makePayment instead of pay) and different parameter types.

cpp
// Target Interface expected by our system
class PaymentGateway {
public:
    virtual void pay(const string& orderId, double amount) = 0;
};

// Existing incompatible class (Adaptee)
class RazorpayAPI {
public:
    // Different method signature!
    void makePayment(const string& invoiceId, double amountInRupees) {
        cout << "Paid via Razorpay: " << amountInRupees << "\n";
    }
};

// ❌ The Client cannot use RazorpayAPI directly!
class CheckoutService {
    shared_ptr<PaymentGateway> gateway;
public:
    void checkout() {
        gateway->pay("123", 500); // RazorpayAPI doesn't have pay()
    }
};

🛠️ The Solution: The Adapter

We create a RazorpayAdapter class that implements our PaymentGateway interface but internally delegates the work to RazorpayAPI.

cpp
// 1. Target Interface
class PaymentGateway {
public:
    virtual ~PaymentGateway() = default;
    virtual void pay(const string& orderId, double amount) = 0;
};

// 2. The Adaptee (Incompatible)
class RazorpayAPI {
public:
    void makePayment(const string& invoiceId, double amountInRupees) {
        cout << "Paid Rs. " << amountInRupees << " via Razorpay for invoice: " << invoiceId << "\n";
    }
};

// 3. The Adapter
class RazorpayAdapter : public PaymentGateway {
private:
    shared_ptr<RazorpayAPI> razorpayAPI;

public:
    RazorpayAdapter() {
        razorpayAPI = make_shared<RazorpayAPI>();
    }

    // Translates the expected interface to the Adaptee's interface
    void pay(const string& orderId, double amount) override {
        // We map 'orderId' to 'invoiceId' under the hood
        razorpayAPI->makePayment(orderId, amount);
    }
};

// 4. Client Code
int main() {
    // Client treats it like a standard PaymentGateway
    shared_ptr<PaymentGateway> gateway = make_shared<RazorpayAdapter>();
    gateway->pay("ORDER_999", 1500.00); 
}

✅ Pros and Cons

ProsCons
Reusability: Reuses existing legacy or 3rd-party code without changing its sourceComplexity: Adds an extra layer of abstraction
OCP Compliant: You can add adapters for new services without modifying client codeOveruse: Sometimes it's better to just refactor the Adaptee if you own the code

[!quote] Key Takeaway Use the Adapter Pattern when you want to use an existing class, but its interface doesn't match what your system expects (especially common when integrating third-party libraries or legacy code).
