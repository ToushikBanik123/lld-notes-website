📌 Decorator Pattern

🎯 What is the Decorator Pattern?

The Decorator Pattern allows behavior to be added to individual objects, dynamically at runtime, without affecting the behavior of other objects from the same class.

It wraps an object inside another object (a wrapper) that adds new behaviors, while keeping the original object's interface intact.

[!example] Real-World Analogy ☕ Think of a Coffee Shop. You order a BasicCoffee. Then you want to add Milk, Sugar, and Caramel. You don't need a CaramelSugarMilkCoffee class. Instead, you take the base coffee, wrap it in a Milk decorator, wrap that in a Sugar decorator, etc. Each layer adds to the price and description.

⚠️ The Problem: Class Explosion via Inheritance

Imagine building a Pizza ordering system using inheritance to add toppings.

cpp
// ❌ BAD PRACTICE — Inheritance explosion
class PlainPizza {};
class CheesePizza : public PlainPizza {};
class OlivePizza : public PlainPizza {};
class CheeseOlivePizza : public CheesePizza {};
class CheeseOliveStuffedCrustPizza : public CheeseOlivePizza {};
// ... 100 more combinations!

Every new topping doubles the number of classes required! Inheritance is rigid and determined at compile-time.

🛠️ The Solution: Composition & Wrappers

We create Decorators that implement the exact same interface as the base object, but also contain a reference to an object of that interface.

1. Component Interface & Base Class

cpp
class Pizza {
public:
    virtual ~Pizza() = default;
    virtual string getDescription() const = 0;
    virtual double getCost() const = 0;
};

// Base Component
class MargheritaPizza : public Pizza {
public:
    string getDescription() const override { return "Margherita Pizza"; }
    double getCost() const override { return 200.00; }
};

2. The Abstract Decorator

cpp
// Implements Pizza, AND holds a reference to a Pizza
class PizzaDecorator : public Pizza {
protected:
    shared_ptr<Pizza> pizza; // The object being wrapped

public:
    explicit PizzaDecorator(shared_ptr<Pizza> p) : pizza(std::move(p)) {}
};

3. Concrete Decorators

cpp
class ExtraCheese : public PizzaDecorator {
public:
    explicit ExtraCheese(shared_ptr<Pizza> p) : PizzaDecorator(std::move(p)) {}

    string getDescription() const override {
        return pizza->getDescription() + ", Extra Cheese"; // Add behavior
    }

    double getCost() const override {
        return pizza->getCost() + 40.0; // Add cost
    }
};

class Olives : public PizzaDecorator {
public:
    explicit Olives(shared_ptr<Pizza> p) : PizzaDecorator(std::move(p)) {}

    string getDescription() const override {
        return pizza->getDescription() + ", Olives";
    }

    double getCost() const override {
        return pizza->getCost() + 30.0;
    }
};

4. Client Code (Layering)

cpp
int main() {
    // 1. Base Pizza
    shared_ptr<Pizza> myPizza = make_shared<MargheritaPizza>();

    // 2. Wrap it with Cheese
    myPizza = make_shared<ExtraCheese>(myPizza);

    // 3. Wrap it with Olives
    myPizza = make_shared<Olives>(myPizza);

    // Final result triggers a chain of calls inward, and builds outward!
    cout << myPizza->getDescription(); 
    // Output: Margherita Pizza, Extra Cheese, Olives
    cout << myPizza->getCost(); // 270.0
}

✅ Pros and Cons

ProsCons
Dynamic Flexibility: Add or remove responsibilities at runtimeSmall Object Proliferation: Can result in many tiny wrapper classes
Avoids Subclass Explosion: Composition over inheritanceDebugging is harder: Following the call stack through 10 wrappers can be tedious
SRP Compliant: Each decorator focuses on one specific add-onOrder Sensitivity: Sometimes the order in which decorators are applied matters

[!quote] Key Takeaway Use the Decorator pattern when you need to dynamically assign extra behaviors to objects at runtime without breaking the code that uses these objects. It acts like a "matryoshka doll" of objects.
