📌 Composite Pattern

🎯 What is the Composite Pattern?

The Composite Pattern allows you to compose objects into tree structures to represent part-whole hierarchies.

Most importantly, it allows clients to treat individual objects and collections of objects uniformly (in the exact same way).

[!example] Real-World Analogy 📦 Think of an Amazon Shopping Cart. You can add an individual Product (like a Book) to the cart. You can also add a ProductBundle (like an "iPhone Combo" containing a phone, charger, and headphones). When you click "Checkout", the system just calls getPrice() on everything in the cart. It shouldn't care whether an item is a single Product or a nested Bundle.

⚠️ The Problem: Manual Branching

If Product and ProductBundle don't share an interface, your client code becomes a mess of if/else checks:

cpp
// ❌ BAD PRACTICE
double calculateTotal(vector<Object> cart) {
    double total = 0;
    for (auto item : cart) {
        if (typeof(item) == "Product") {
            total += item.getPrice();
        } else if (typeof(item) == "Bundle") {
            // Unpack bundle and loop through its contents manually...
        }
    }
    return total;
}

This breaks Polymorphism and scales very poorly. Also, you can't easily put a Bundle inside another Bundle.

🛠️ The Solution: The Component Interface

We create a common interface (CartItem) for both the Leaves (individual products) and the Composites (bundles).

1. Component Interface

cpp
class CartItem {
public:
    virtual ~CartItem() = default;
    virtual double getPrice() const = 0;
    virtual void display(const string& indent) const = 0;
};

2. The Leaf (Individual Object)

cpp
class Product : public CartItem {
    string name;
    double price;
public:
    Product(const string& n, double p) : name(n), price(p) {}

    double getPrice() const override {
        return price;
    }

    void display(const string& indent) const override {
        cout << indent << "Product: " << name << " - Rs." << price << "\n";
    }
};

3. The Composite (Container)

cpp
class ProductBundle : public CartItem {
    string bundleName;
    vector<shared_ptr<CartItem>> items; // Can hold Products OR other Bundles!

public:
    ProductBundle(const string& name) : bundleName(name) {}

    void addItem(const shared_ptr<CartItem>& item) {
        items.push_back(item);
    }

    // Recursively sum up the prices of all children
    double getPrice() const override {
        double total = 0;
        for (const auto& item : items) {
            total += item->getPrice();
        }
        return total;
    }

    void display(const string& indent) const override {
        cout << indent << "Bundle: " << bundleName << "\n";
        for (const auto& item : items) {
            item->display(indent + "  "); // Recursive display
        }
    }
};

4. Client Code

cpp
int main() {
    auto phone = make_shared<Product>("iPhone", 80000);
    auto charger = make_shared<Product>("Charger", 2000);
    
    auto combo = make_shared<ProductBundle>("iPhone Combo");
    combo->addItem(phone);
    combo->addItem(charger);

    // Treat leaf and composite uniformly!
    vector<shared_ptr<CartItem>> cart = { phone, combo };
    
    double total = 0;
    for(auto item : cart) {
        total += item->getPrice(); // Polymorphism handles the rest!
    }
}

✅ Pros and Cons

ProsCons
Uniformity: Client treats all elements in the tree exactly the same wayOvergeneralized: Can make the design too general. Sometimes you want to restrict what can be added to a composite (e.g., a "HardwareBundle" shouldn't accept "SoftwareProduct").
Extensible: Easily add new types of leaves or composites
Recursive Data: Perfect for handling trees, file systems, nested menus, UI components

[!quote] Key Takeaway Use the Composite pattern when you have data organized in a tree-like, part-whole hierarchy (like folders and files, or nested product bundles), and you want client code to ignore the difference between simple items and complex containers.
