📌 API Design, Versioning, and Security

🌐 Principles of API Design

An API is a strict contract between the frontend (or third-party clients) and your backend services. Good APIs are Predictable, Consistent, and Stateless.

REST Best Practices

  1. Nouns, not Verbs: Use /users/123, NOT /getUser/123.
  2. HTTP Verbs: Use GET (read), POST (create), PUT (full update), PATCH (partial update), and DELETE (remove) correctly.
  3. Idempotency: Calling PUT or DELETE multiple times should have the same effect as calling it once.
  4. HATEOAS: Provide hypermedia links in responses to guide the client to the next available actions.

📦 The DTO Pattern (Data Transfer Object)

Never expose your internal Database Entities directly to the API! Use DTOs.

cpp
// Internal Entity (Never expose password Hash or DB internal fields!)
class UserEntity {
    long id;
    string name;
    string passwordHash;
    string dbSyncToken;
};

// What the API Returns
class UserResponseDTO {
    long id;
    string name;
};

Why DTOs?

  1. Security: Prevents accidental leakage of sensitive fields.
  2. Decoupling: You can change your database schema without breaking the API contract for clients.
  3. Validation: Input DTOs (CreateUserRequestDTO) can enforce strict validation (e.g., email format) at the edge of the system.

🚦 Error Handling

A robust API should never return an HTML stack trace. Always return structured JSON errors with appropriate HTTP Status codes.

Standard HTTP Codes:

  • 200/201: Success / Created
  • 400: Bad Request (Client's fault - bad input)
  • 401/403: Unauthorized / Forbidden
  • 404: Not Found
  • 500: Internal Server Error (Backend crashed)

Standard Error Response Format:

json
{
  "timestamp": "2026-06-12T10:23:00Z",
  "status": 400,
  "error": "Bad Request",
  "message": "Missing required field: email",
  "path": "/api/users"
}

🔄 API Versioning

If you need to change the API contract (e.g., renaming fields), you must NOT break existing clients. You do this via Versioning.

  1. URI Versioning (Most Common): /api/v1/users -> /api/v2/users
  2. Header Versioning: Passing a custom header X-API-Version: 2
  3. Media Type Versioning: Passing Accept: application/vnd.company.v2+json

[!tip] Best Practice Only introduce breaking changes in new versions. Support the old version alongside the new one, give clients a timeline, and deprecate it gracefully.

🔒 Security, Throttling, and Rate Limiting

  1. Authentication: Use stateless tokens (JWT or OAuth2) to verify who the user is.
  2. Authorization: Check if the user has permission to do the action (RBAC).
  3. Rate Limiting: Restrict a user to X requests per minute. Returns 429 Too Many Requests. This prevents brute-force attacks and limits cloud costs.
  4. Throttling: Slowly delay responses if a user is hitting the API too fast, before fully blocking them.
