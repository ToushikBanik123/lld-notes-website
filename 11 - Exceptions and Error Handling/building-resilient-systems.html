🛡️ Robust vs Brittle Systems

A Brittle System crashes completely when a single component fails. (e.g., Amazon checkout fails entirely if the recommendation engine goes down).

A Robust System absorbs failures and degrades gracefully. It continues to provide service, even if with limited functionality.

📉 Graceful Degradation Strategies

If an external API or service fails, use these strategies to keep the user experience intact.

1. Return Cached Data

If the live service is down, return slightly stale data instead of an error. Perfect for recommendation engines or news feeds.

cpp
try {
    return fetchLiveRecommendations();
} catch (const exception& ex) {
    return fetchCachedRecommendations(); // Fallback to cache
}

2. Show Fallback UI

Provide a default view or message instead of a broken screen. Example: return Menu("Menu currently unavailable. Please try again later.");

3. Queue Requests

If a payment system is temporarily overwhelmed, don't drop the order. Add it to a queue and process it silently in the background when the system recovers.

🔄 Retry Mechanisms

For temporary failures (like a network blip), automatically retrying can save the user experience. However, beware of causing a self-inflicted DDoS attack if thousands of users retry simultaneously!

The Backoff Strategy (Exponential Backoff)

Instead of retrying immediately, add a progressively increasing delay between attempts.

cpp
string getETAWithBackoff() {
    int retries = 3;
    int delay_ms = 1000; // Start with 1 second

    while (retries-- > 0) {
        try {
            return fetchLiveETA();
        } catch (const exception& e) {
            this_thread::sleep_for(chrono::milliseconds(delay_ms));
            delay_ms *= 2; // Double the delay! (1s -> 2s -> 4s)
        }
    }
    return "ETA unavailable";
}

🔌 The Circuit Breaker Pattern

If a downstream service is completely dead, repeatedly retrying is a waste of CPU, network resources, and adds massive latency.

The Circuit Breaker pattern monitors a service. If failures cross a threshold, the circuit "opens" and instantly returns a fallback without even attempting to call the dead service.

The 3 States

  1. Closed (Normal): Requests flow freely.
  2. Open (Failing): Failures exceeded threshold. Requests are immediately rejected / sent to fallback.
  3. Half-Open (Testing): After a timeout, allows a few requests through to test if the service has recovered. If they succeed, it closes. If they fail, it opens again.
cpp
class PaymentService {
    int failureCount = 0;
    bool circuitOpen = false;

public:
    string charge() {
        if (circuitOpen) return "PAYMENT_FAILED_FALLBACK"; // Instant return!

        try {
            // Attempt live payment...
            throw runtime_error("Service Down");
        } catch (const exception& e) {
            failureCount++;
            if (failureCount >= 3) {
                circuitOpen = true; // Trip the breaker!
            }
            return "PAYMENT_FAILED_FALLBACK";
        }
    }
};

⏱️ Timeouts and Failovers

1. Timeouts

Never wait indefinitely for a response. If a database is locked, a hanging thread will eventually exhaust system resources. Set strict Timeouts (e.g., 2 seconds) and abort the request.

2. Failover

Proactively switch to a standby alternative. Example: If Razorpay is unresponsive (Timeout), automatically reroute the payment request to Stripe (Failover) without the user noticing.
