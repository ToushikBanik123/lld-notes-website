Dependency Inversion Principle (DIP)

lldsoliddip

📌 Dependency Inversion Principle (DIP)

[!info] Navigation Module: [[00 - Course Overview/index|← Course Overview]] Prev: [[04 - SOLID Principles/interface-segregation|← ISP]] Next: [[05 - UML Diagrams/intro-to-uml|Introduction to UML →]]

🎯 Definition

[!tip] DIP in One Line High-level modules should not depend on low-level modules. Both should depend on abstractions.

Additionally: Abstractions should not depend on details. Details should depend on abstractions.

🔌 Real-World Analogy

[!example] Electrical Outlets Your laptop charger plugs into a standard outlet (abstraction). It doesn't care if the power comes from solar panels, a generator, or the grid.

If the charger was wired directly to a specific generator (concrete dependency), you'd need to rewire it every time you change the power source. 😬

💻 Code Example

❌ Violating DIP — Direct Dependency

cpp
// Low-level module
class MySQLDatabase {
public:
    void save(string data) {
        cout << "Saving to MySQL: " << data << endl;
    }
};

// High-level module — DIRECTLY depends on MySQL
class UserService {
    MySQLDatabase db;  // ❌ Tightly coupled to MySQL!
public:
    void createUser(string name) {
        db.save(name);
    }
};
// Problem: Switching to PostgreSQL requires changing UserService!

✅ Following DIP — Depending on Abstractions

cpp
// Abstraction (interface)
class Database {
public:
    virtual void save(string data) = 0;
    virtual ~Database() {}
};

// Low-level modules implement the abstraction
class MySQLDatabase : public Database {
public:
    void save(string data) override {
        cout << "Saving to MySQL: " << data << endl;
    }
};

class PostgreSQLDatabase : public Database {
public:
    void save(string data) override {
        cout << "Saving to PostgreSQL: " << data << endl;
    }
};

// High-level module — depends on ABSTRACTION
class UserService {
    Database* db;  // ✅ Depends on interface, not concrete class
public:
    UserService(Database* database) : db(database) {}
    void createUser(string name) { db->save(name); }
};

int main() {
    MySQLDatabase mysql;
    UserService service1(&mysql);     // Works with MySQL
    service1.createUser("Alice");

    PostgreSQLDatabase postgres;
    UserService service2(&postgres);  // Works with PostgreSQL too!
    service2.createUser("Bob");
}

🔄 Dependency Inversion vs Dependency Injection

ConceptWhat It Is
Dependency Inversion (DIP)A principle — depend on abstractions, not concretions
Dependency Injection (DI)A technique — pass dependencies from outside instead of creating them inside

[!tip] Relationship DI is one way to implement DIP. You "inject" the abstraction into the class via constructor, setter, or method parameter.

✅ Benefits

BenefitExplanation
Loose couplingHigh-level code doesn't know about low-level details
Easy to swapChange database/API without touching business logic
TestabilityInject mock dependencies for unit testing
ExtensibilityAdd new implementations without changing existing code

📊 SOLID Summary

PrincipleCore RuleViolation Signal
S — SRPOne class, one reason to changeClass does too many things
O — OCPExtend, don't modifyAdding features requires changing existing code
L — LSPSubclasses must be substitutableChild breaks parent's contract
I — ISPSmall, focused interfacesEmpty method implementations
D — DIPDepend on abstractionsnew ConcreteClass() inside business logic

[!quote] Key Takeaway Depend on abstractions, not concretions. When your high-level business logic doesn't know (or care) about low-level implementation details, your architecture becomes truly flexible.
