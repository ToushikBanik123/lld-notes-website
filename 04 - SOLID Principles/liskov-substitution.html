Liskov Substitution Principle (LSP)

lldsolidlsp

📌 Liskov Substitution Principle (LSP)

[!info] Navigation Module: [[00 - Course Overview/index|← Course Overview]] Prev: [[04 - SOLID Principles/open-closed|← OCP]] Next: [[04 - SOLID Principles/interface-segregation|Interface Segregation (ISP) →]]

🎯 Definition

[!tip] LSP in One Line If S is a subtype of T, then objects of type T can be replaced with objects of type S without breaking the program.

Any subclass should be substitutable for its parent class without altering correctness.

🐍 Real-World Analogy

[!example] Pet Hotel Your pet hotel handles all pets: dogs, cats, rabbits — all can be fed, walked, and groomed. ✅

Someone brings a pet snake:

  • Walk it? ❌ Can't.
  • Groom it? ❌ Doesn't make sense.
  • Feed it regular food? ❌ Needs live mice.

The snake breaks the system's expectations — this is an LSP violation!

A hamster would be fine — it still fits the expected "pet" behavior (just a wheel instead of walking). ✅

💻 The Classic Rectangle-Square Problem

❌ Violating LSP

cpp
class Rectangle {
protected:
    int width, height;
public:
    virtual void setWidth(int w) { width = w; }
    virtual void setHeight(int h) { height = h; }
    int getArea() { return width * height; }
};

class Square : public Rectangle {
public:
    void setWidth(int w) override {
        width = w;
        height = w;  // Forces both to be equal!
    }
    void setHeight(int h) override {
        height = h;
        width = h;   // Forces both to be equal!
    }
};

void printArea(Rectangle* r) {
    r->setWidth(5);
    r->setHeight(10);
    cout << r->getArea() << endl;
    // Expected: 50
    // Actual with Square: 100 💥
}

✅ Following LSP — Notification System

cpp
class Notification {
public:
    virtual void sendNotification() {
        cout << "Notification sent" << endl;
    }
    virtual ~Notification() {}
};

class EmailNotification : public Notification {
public:
    void sendNotification() override {
        cout << "Email Notification sent 📧" << endl;
    }
};

class TextNotification : public Notification {
public:
    void sendNotification() override {
        cout << "Text Notification sent 📱" << endl;
    }
};

// This works perfectly with ANY notification type!
void notify(Notification* n) {
    n->sendNotification();  // Always works correctly ✅
}

int main() {
    Notification* n = new EmailNotification();
    notify(n);  // "Email Notification sent 📧"
    delete n;

    n = new TextNotification();
    notify(n);  // "Text Notification sent 📱"
    delete n;
}

🔍 How to Spot LSP Violations

Warning SignQuestion to Ask
Override changes meaningDoes the subclass change the expected behavior of a parent method?
Throws unexpected exceptionsDoes the subclass throw errors the parent doesn't?
Substitution breaks testsCan you replace parent with child everywhere without issues?
Weakens/strengthens conditionsDoes the subclass tighten preconditions or loosen postconditions?

🔑 Key Principles to Follow

  • Subclasses should honor the contract of the parent class
  • Avoid overriding methods in ways that change behavior drastically
  • Prefer composition over inheritance when the IS-A relationship isn't clean
  • Think in terms of behavioral compatibility, not just type hierarchy

[!quote] Key Takeaway If you can replace a parent class with a child class everywhere and nothing breaks, your design follows LSP. If substitution causes surprises, rethink the hierarchy.
