Interface Segregation Principle (ISP)

lldsolidisp

📌 Interface Segregation Principle (ISP)

[!info] Navigation Module: [[00 - Course Overview/index|← Course Overview]] Prev: [[04 - SOLID Principles/liskov-substitution|← LSP]] Next: [[04 - SOLID Principles/dependency-inversion|Dependency Inversion (DIP) →]]

🎯 Definition

[!tip] ISP in One Line No client should be forced to depend on methods it does not use.

Instead of one large, "fat" interface, create multiple small, focused interfaces.

🖨️ Real-World Analogy

[!example] The All-in-One Printer Problem An all-in-one printer can print, scan, fax, and copy.

But a basic home user only needs to print. They shouldn't be forced to deal with fax and scan buttons they'll never use.

ISP says: Give the home user just a Printable interface, not the entire AllInOneMachine interface.

💻 Code Example

❌ Violating ISP — Fat Interface

cpp
// Fat interface — forces ALL implementations to have ALL methods
class Machine {
public:
    virtual void print() = 0;
    virtual void scan() = 0;
    virtual void fax() = 0;
    virtual ~Machine() {}
};

class BasicPrinter : public Machine {
public:
    void print() override { cout << "Printing..." << endl; }
    void scan() override { /* 😬 Does nothing! */ }
    void fax() override { /* 😬 Does nothing! */ }
};

[!warning] Problem BasicPrinter is forced to implement scan() and fax() even though it can't do either. This leads to empty methods, throwing exceptions, or misleading behavior.

✅ Following ISP — Segregated Interfaces

cpp
class Printable {
public:
    virtual void print() = 0;
    virtual ~Printable() {}
};

class Scannable {
public:
    virtual void scan() = 0;
    virtual ~Scannable() {}
};

class Faxable {
public:
    virtual void fax() = 0;
    virtual ~Faxable() {}
};

// Basic printer — only implements what it can do
class BasicPrinter : public Printable {
public:
    void print() override { cout << "Printing..." << endl; }
};

// Advanced printer — implements everything
class AdvancedPrinter : public Printable, public Scannable, public Faxable {
public:
    void print() override { cout << "Printing (advanced)..." << endl; }
    void scan() override { cout << "Scanning..." << endl; }
    void fax() override { cout << "Faxing..." << endl; }
};

🔍 Signs You're Violating ISP

SignProblem
Empty method implementationsClass can't actually do what the interface requires
throw UnsupportedOperationException()Runtime failures for unsupported features
Clients importing methods they don't useUnnecessary coupling
Interface has 10+ methodsProbably a "fat" interface

✅ Benefits

BenefitExplanation
Reduced couplingClients depend only on what they need
Easier to implementSmaller interfaces are simpler to implement
Better maintainabilityChanges to one interface don't affect unrelated clients
Clearer contractsEach interface has a focused purpose

[!quote] Key Takeaway Many small interfaces > one large interface. Don't force classes to implement methods they can't use. Keep interfaces focused and role-specific.
