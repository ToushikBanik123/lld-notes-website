📌 Open/Closed Principle (OCP)

[!info] Navigation Module: [[00 - Course Overview/index|← Course Overview]] Prev: [[04 - SOLID Principles/single-responsibility|← SRP]] Next: [[04 - SOLID Principles/liskov-substitution|Liskov Substitution (LSP) →]]

🎯 Definition

[!tip] OCP in One Line Software entities should be open for extension, but closed for modification.

You should be able to add new behavior without changing existing, tested code.

🔌 Real-World Analogy

[!example] Travel Adapter Your Indian charger doesn't fit UK sockets. Instead of modifying the charger, you use a travel adapter.

  • The adapter extends your charger's capability
  • You didn't modify the charger itself

💻 Code Example — Tax Calculator

❌ Violating OCP

cpp
class InvoiceProcessor {
public:
    double calculateTotal(string region, double amount) {
        if (region == "India") return amount + amount * 0.18;
        else if (region == "US") return amount + amount * 0.08;
        else if (region == "UK") return amount + amount * 0.12;
        // Adding Germany? Must MODIFY this method ❌
        return amount;
    }
};

[!warning] Problem Every new region requires modifying this class. Risk of breaking existing logic.

✅ Following OCP

cpp
// Strategy Interface
class TaxCalculator {
public:
    virtual double calculateTax(double amount) = 0;
    virtual ~TaxCalculator() {}
};

class IndiaTaxCalculator : public TaxCalculator {
public:
    double calculateTax(double amount) override { return amount * 0.18; }
};

class USTaxCalculator : public TaxCalculator {
public:
    double calculateTax(double amount) override { return amount * 0.08; }
};

class UKTaxCalculator : public TaxCalculator {
public:
    double calculateTax(double amount) override { return amount * 0.12; }
};

// Invoice — CLOSED for modification
class Invoice {
    double amount;
    TaxCalculator* taxCalc;
public:
    Invoice(double amt, TaxCalculator* tc) : amount(amt), taxCalc(tc) {}
    double getTotal() { return amount + taxCalc->calculateTax(amount); }
};

🕐 When to Apply OCP

Apply WhenDon't Apply When
Module is expected to evolveSmall, simple projects
Building extensible systems (plugins, engines)Feature is a one-off
Protecting stable, production-ready codePrematurely — wait for patterns of change
A class is becoming a "God class"It adds unnecessary abstraction

⚠️ Common Misconceptions

MythReality
"Code should never be changed again"OCP means avoid changing core logic, not all code
"OCP creates too many classes"More classes = better modularity and testability
"Refactoring contradicts OCP"Refactoring is often a step toward OCP compliance
"Always apply OCP upfront"Apply in response to observed patterns of change

[!quote] Key Takeaway Design your system so that adding new features means writing new code, not changing old code. This is the heart of extensible software.
