📌 Single Responsibility Principle (SRP)

[!info] Navigation Module: [[00 - Course Overview/index|← Course Overview]] Prev: [[04 - SOLID Principles/overview|← SOLID Overview]] Next: [[04 - SOLID Principles/open-closed|Open/Closed (OCP) →]]

🎯 Definition

[!tip] SRP in One Line A class should have only one reason to change. In other words, a class should have only one job, one responsibility, and one purpose.

If a class takes on multiple responsibilities, they become coupled. A change in one responsibility may affect others, creating a ripple effect of bugs.

🍳 Real-World Analogy

[!example] The Chef Problem Imagine a chef responsible for cooking, cleaning, serving, AND ordering groceries. If the chef is busy cleaning, cooking quality suffers.

Solution: Separate roles — Chef cooks, Cleaner cleans, Waiter serves, Manager orders. Each person focuses on their specific job = better results.

💻 Code Example

❌ Violating SRP

cpp
// One class doing EVERYTHING — violates SRP
class TUFplusCompiler {
public:
    void addDriverCode() { /* ... */ }
    void performSyntaxCheck() { /* ... */ }
    void runTestCases() { /* ... */ }
    void storeOutputInDB() { /* ... */ }      // DB logic!
    void returnOutputToUser() { /* ... */ }   // UI logic!
};

[!warning] Problem If the database changes, you modify this class. If the UI changes, you modify this class. One class, many reasons to change.

✅ Following SRP

cpp
class DriverCodeGenerator {
public:
    void addDriverCode() { /* ... */ }
};

class SyntaxChecker {
public:
    void performSyntaxCheck() { /* ... */ }
};

class TestRunner {
public:
    void runWithTestCases() { /* ... */ }
};

class DatabaseManager {
public:
    void storeOutput() { /* ... */ }
};

class UserOutputHandler {
public:
    void returnOutput() { /* ... */ }
};

// Coordinator ties everything together
class CompilerCoordinator {
    DriverCodeGenerator driverGen;
    SyntaxChecker syntaxChecker;
    TestRunner testRunner;
    DatabaseManager dbManager;
    UserOutputHandler outputHandler;

public:
    void compile() {
        driverGen.addDriverCode();
        syntaxChecker.performSyntaxCheck();
        testRunner.runWithTestCases();
        dbManager.storeOutput();
        outputHandler.returnOutput();
    }
};

✅ Advantages

BenefitExplanation
Improved MaintainabilityChanges in one part don't affect others
Enhanced ReadabilitySmaller, focused classes are easier to understand
Better ReusabilitySingle-purpose classes can be reused elsewhere
Facilitates TestingFewer dependencies = easier to test
Lower RiskChanges are less likely to cause side effects

⚠️ Common SRP Violations

ViolationProblem
Mixing DB logic with business logicCan't change DB without affecting business rules
Coupling UI code with business logicCan't change UI without touching core logic
Logging + processing in one classLogging changes break processing

🔍 SRP Beyond Classes

[!important] SRP is a Mindset SRP applies to methods, modules, microservices, and even entire systems — not just classes.

The key question: "Does this component have a single reason to change?"

[!quote] Key Takeaway One class, one job. If you can describe what a class does using the word "AND", it probably has too many responsibilities.
